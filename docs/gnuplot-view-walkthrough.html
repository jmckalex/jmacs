Motivation: an interactive gnuplot notebook inside Godot

gnuplot is one of those tools you reach for in bursts. You want to see sin(x), then sin(x), cos(x), then the same thing with a title and a tighter yrange — each command a small refinement of the last. The natural shape of that work is a conversation: a running session you talk to, where earlier commands stay on screen and the next one builds on them. A one-shot gnuplot script.gp invocation throws that context away every time. An interactive terminal session keeps the process alive, but on most platforms gnuplot's interactive plot lands in a separate OS window that floats outside the editor, has its own dark/light assumptions, and disappears the moment you plot again.

What we build in this walkthrough is the middle path: a gnuplot view that lives inside Godot as a notebook REPL. One long-lived gnuplot child process per view; an input line at the bottom; and a scrolling transcript above it where every command you submit becomes a cell holding its result — an inline SVG plot, text output from print/show, or a red error. The plot renders in the document, themed to match the editor, and it stays put. Your previous five plots scroll up; you can read your whole exploratory session at a glance.

The Lisp command that opens one is the entire user-facing surface:

(defcommand gnuplot ()
  "Open a fresh gnuplot buffer.

   The buffer that appears is shown through the L4 gnuplot view (not the
   text editor view) — a notebook REPL. Type a gnuplot command at the
   input line and press Enter to run it; the plot (or text / error
   output) appears as a cell above. Use Up and Down to recall previous
   commands; press C-c to interrupt a long-running plot.

   Each call to `gnuplot` creates a new buffer — switch back to an open
   one by name with `C-x b`. If gnuplot is not installed, the view shows
   install instructions (`brew install gnuplot`)."
  (open-gnuplot-buffer!))

You invoke it with M-x gnuplot or the chord C-c g, bound by symbol in the c-c-keymap so the command resolves at dispatch time and load order never matters: 

(define c-c-keymap
  {"tab"       'toggle-fold-at-point
   ;; ...
   ;; C-c g opens a gnuplot buffer (see gnuplot.lisp). Bound by symbol;
   ;; the command resolves at dispatch time, so load order doesn't matter.
   "g"         'gnuplot})

Why a notebook, and why these specific design choices

The view deliberately mirrors Godot's existing shell view — same factory-plus-custom-element shape, same hide-not-kill lifecycle — but the interaction model is different, and that difference drives every decision in the rest of this walkthrough. A shell streams raw pty bytes into an xterm grid; there's no notion of "one command, one result." gnuplot in pipe mode does have that notion: you feed it a command, it draws a plot and maybe prints some text. So instead of a terminal grid, the view is built from three parts: 

// instead of an xterm grid the view holds:
//   - a header (chart icon + buffer name + a plot-theme picker),
//   - a scrollable transcript of per-command cells, and
//   - a bottom input line with its own command history (Up/Down).

Three consequences fall out of choosing a notebook over a terminal, and each is a section of this walkthrough:

  • The host must frame each submission, not just forward bytes. A terminal can pipe stdout through verbatim; a notebook needs to know when one command's output ends and the next begins. The host wraps every user command in a preambleepilogue that routes the plot to a temp SVG file and emits two sentinel tokens, and a submission only completes/ when both sentinels arrive.
  • The view needs its own command history. The shell view keeps no history — the child shell's readline owns Up/Down. A bare <input> has no readline, so we implement a small history ring ourselves (and unit-test it without a DOM).
  • The plot must be themed by us, not by gnuplot's defaults. gnuplot's stock SVG is white-on-white. To sit in a dark editor it has to be re-themed at render time — a dark background baked into the SVG, axis and grid colours, and a redefined line-type palette so a bare plot sin(x), cos(x) picks up two distinct, legible colours.

A tour of the finished view

A cell is created the moment you press Enter — echoed with its command and marked pending — and keyed by the submission id the host will later echo back. When the result arrives, it's matched to that cell and filled in. This echo-then-fill pattern is what makes the session feel responsive even though the plot render is asynchronous:

function runCommand(cmd) {
  if (!buffer || buffer.ended) return;

  const cell = doc.createElement('div');
  cell.className = 'gnuplot-cell gnuplot-cell-pending';
  // ...echo the command into the cell...
  transcriptEl.append(cell);
  scrollToEnd();

  // We track our own parallel counter so we can key the cell before the
  // result returns.
  buffer.submitCounter = (buffer.submitCounter ?? 0) + 1;
  const id = buffer.submitCounter;
  cellsById.set(id, cell);

  if (writeFn) {
    writeFn(buffer.sessionId, cmd).catch(() => {
      markCellError(cell, '[gnuplot write failed]');
    });
  }
}

A cell can end up as any of a handful of shapes — a plot (possibly with a muted warning under it), text, a red error, or a dim (no output) acknowledgement for a bare set — and the same result handler decides which, based purely on what the host sent back in the { svg, text, error } payload. The plot SVG is inlined (not wrapped in an <img> data-URL) so it scales with the cell; it's trusted-local markup with <script> already stripped main-side: 

// The SVG is trusted-local (generated by the host's own gnuplot,
// scripts already stripped main-side); inline it so it scales with the cell.
if (typeof payload.svg === 'string' && payload.svg !== '') {
  const plot = doc.createElement('div');
  plot.className = 'gnuplot-cell-plot';
  plot.innerHTML = payload.svg;
  cell.append(plot);
}

When gnuplot isn't installed

A view that hard-crashes when its backing tool is missing is a bad citizen in an editor people open every day. gnuplot is frequently not installed, and spawn('gnuplot', …) doesn't even throw synchronously for a missing binary — it emits an async error event with code === 'ENOENT' a tick later. The host turns that into a distinct exit signal, and the view replaces its transcript with a friendly install card and disables the input rather than showing a stack trace: 

if (payload.notInstalled) {
  transcriptEl.replaceChildren();
  cellsById.clear();
  const card = doc.createElement('div');
  card.className = 'gnuplot-not-installed';
  // ...chart icon + message...
  msg.textContent = payload.message ?? DEFAULT_NOT_INSTALLED;
  card.append(icon, msg);
  transcriptEl.append(card);
  input.disabled = true;
  input.placeholder = 'gnuplot unavailable';
  return;
}

Note. The plot-rendering paths are unit-tested as pure logic — three fast suites covering quoting, submission framing (including the themes), the SVG-has-plot heuristic, the stream demux, the history ring, and the export sizing — and the protocol has been smoke-tested against a real gnuplot 6, which is also what produced the genuine plots embedded throughout this page.

Architecture: what a "view kind" actually is in Godot

Before any gnuplot code, you have to understand the shape of the hole you are filling. In Godot, the editor does not have one canvas that everything draws into. It has a family of view kinds — text, image, pdf, browser, jukebox, directory-tree, shell — and a new kind is not a special case bolted onto the editor core. It is an assembly of five small, independently-replaceable parts that already have well-defined seams. The discipline of the build was to add nothing new to the framework: every part of gnuplot slots into a socket that the shell view defined first. (The general recipe for adding a kind is docs/CUSTOM-VIEWS.md; the key-dispatch side is docs/MODEL-B-DISPATCH.md. This walkthrough is the long-form worked example.)

One orientation fact first: Godot's Lisp world does not run inside the window. It runs in the spine — a central Lisp server (an Electron utilityProcess) that owns the buffers and resolves every keystroke; each window is a thin client. So "the Lisp surface" of a view kind executes server-side, and the window's job is purely to render.

A view kind, concretely, is these five things:

  1. A renderer custom element (L4) — a <gnuplot-view> DOM element that owns the on-screen surface and the user interaction. It knows nothing about subprocesses or IPC channel names; it is handed a bag of callbacks.
  2. A host configure-factory — a plain function in app.js (configureGnuplotView()) that fills that bag of callbacks with the real IPC bindings, so the element can be tested with fakes and run with the real bridge.
  3. A main-process host — the privileged side (gnuplot.js) that owns the actual gnuplot child process, the filesystem, and the dangerous powers the renderer is not allowed to touch.
  4. A Lisp surface — the (gnuplot) command, a mode label, and a keybinding, which is how the kind becomes reachable to the user without hard-coding it into the host. Under the server architecture this is a spine host primitive plus a stdlib file loaded by the spine (SPINE_STDLIB).
  5. A server-side data-source — the spine's record of the open view (its name, session id and working directory), which is what pane layouts point at and what workspace save/restore serialises.

The big picture

The renderer custom element — and why it owns no powers

The view is an HTML custom element, <gnuplot-view>, that extends a shared ViewElement base. The element is deliberately ignorant: it never imports electron, never names an IPC channel, never spawns anything. It is handed a plain options object of callbacks at configure() time and it calls those. That is the whole contract. 

export class GnuplotView extends ViewElement {
  configure(options) {
    if (this._inner !== null) {
      throw new Error('GnuplotView.configure: cannot reconfigure after mount');
    }
    this._options = options ?? null;
  }

  get kind() {
    return 'gnuplot';
  }

  connectedCallback() {
    if (this._inner !== null) return;
    this._inner = createGnuplotView(this, this._options ?? {});
    if (this._pendingBuffer !== null) this._inner.setBuffer(this._pendingBuffer);
  }
}

Why split configure() (set the callbacks) from connectedCallback() (build the DOM)? Because a Godot view is created once and mounted many times. The element is constructed and configured eagerly at startup; the actual inner DOM and history are not built until the element is first connected to the document. <shell-view> has the identical configure-then-build split, for the same reason.

The load-bearing rule. The renderer is sandboxed and untrusted. It cannot read files, cannot spawn processes, cannot run the SVG terminal. Everything dangerous lives behind the context bridge in the host. The view's only privilege is "ask the host to do something, and render what comes back." This is the Electron security model, and every view kind obeys it.

The configure-factory — the IPC seam made explicit

The element wants callbacks; the host exposes IPC. The configure-factory is the one place those two are married. It is a plain function in app.js that returns the options bag, wiring each renderer callback to the corresponding window.host.* bridge method, with a graceful fallback when the bridge is absent: 

function configureGnuplotView() {
  return {
    spawn: (sessionId, opts) =>
      window.host && typeof window.host.gnuplotSpawn === 'function'
        ? window.host.gnuplotSpawn(sessionId, opts)
        : Promise.resolve({ ok: false, error: 'gnuplot IPC unavailable' }),
    write: (sessionId, data) =>
      window.host && typeof window.host.gnuplotWrite === 'function'
        ? window.host.gnuplotWrite(sessionId, data)
        : Promise.resolve({ ok: false }),
    signal:   (sessionId) => /* … gnuplotSignal … */,
    kill:     (sessionId) => /* … gnuplotKill … */,
    onResult: (callback) => /* … onGnuplotResult … */,
    onExit:   (callback) => /* … onGnuplotExit … */,
    // Server-owned: the renderer's chord state is always empty in server
    // mode (keys route to the spine), so a chord is never "in progress"
    // here.
    chordPending: () => false,
    exportSvg: (svg, name) => /* … gnuplotSaveSvg … */,
    setTheme:  (sessionId, theme) => /* … gnuplotSetTheme … */,
    ...serverMediaKeyOption(),
  };
}

Put this next to configureShellView() and the shapes are almost identical — both return spawn / write / kill / onExit plus a stream callback. A few differences carry the whole design distinction between a terminal and a notebook:

  • The shell returns onData — a raw byte stream; the gnuplot view returns onResult — a structured, one-per-submission payload { id, svg, text, error }. That single rename is the difference between "stream a pty into an xterm grid" and "submit a command, get back one cell."
  • The shell carries resize (cols/rows for the pty); gnuplot has no pty, so there is no resize. Instead it carries signal (C-c → SIGINT to interrupt a running plot), plus two notebook affordances the terminal has no use for: exportSvg (save a plot through a native dialog) and setTheme (the header's plot-theme picker).
  • onKey is the chord-forwarding callback that keeps the editor keymap (C-x b to switch buffers, M-x, …) alive while a plain <input> has focus. serverMediaKeyOption() wires it to serverViewClient.dispatchKey, which routes the key string to the spine's keymap — the server resolves every key in Godot (docs/MODEL-B-DISPATCH.md), and a non-text view is no exception. Its companion chordPending tells the view whether a prefix chord is mid-flight; in server mode the renderer never holds chord state, so the factory pins it to () => false and the view's own C-c handling stays conservative (more on this in the input-line section).

The IPC split and the context bridge

The renderer and the main process never share memory; they speak only over Electron IPC, and the renderer can only reach IPC through the context bridge set up in preload.mjs. The bridge exposes a small, named, audited surface — not ipcRenderer itself. The gnuplot surface is eight methods, split into two directions: 

// renderer → host (invoke/return):
gnuplotSpawn:  (sessionId, options = {}) =>
  ipcRenderer.invoke('gnuplot:spawn', { sessionId, cwd: options.cwd }),
gnuplotWrite:  (sessionId, data) =>
  ipcRenderer.invoke('gnuplot:write', { sessionId, data }),
gnuplotSignal: (sessionId) =>
  ipcRenderer.invoke('gnuplot:signal', { sessionId }),
gnuplotKill:   (sessionId) =>
  ipcRenderer.invoke('gnuplot:kill', { sessionId }),
gnuplotSaveSvg: (svg, name) =>
  ipcRenderer.invoke('gnuplot:save-svg', { svg, name }),
gnuplotSetTheme: (sessionId, theme) =>
  ipcRenderer.invoke('gnuplot:set-theme', { sessionId, theme }),

// host → renderer (subscribe, returns an unsubscribe fn):
onGnuplotResult: (callback) => {
  const handler = (_event, payload) => callback(payload);
  ipcRenderer.on('gnuplot:result', handler);
  return () => ipcRenderer.removeListener('gnuplot:result', handler);
},
onGnuplotExit:   (callback) => { /* same shape on 'gnuplot:exit' */ },

Six of the eight are the session's life: spawn it, feed it, interrupt it, kill it, hear its results and its death. The other two are notebook conveniences layered on later: gnuplotSaveSvg writes a plot's SVG to disk through a native save dialog (its handler lives with the other file-dialog code in files.js), and gnuplotSetTheme flips a session's plot palette (handled in gnuplot.js; both are covered in their own sections below).

The asymmetry is deliberate and is the core of the IPC model. Renderer → host calls are requestresponse/ (invoke ⇒ ipcMain.handle): "spawn this," "submit this command," "kill this" — each a one-shot with an acknowledgement. Host → renderer calls are an event stream (webContents.send ⇒ ipcRenderer.on): results and exits arrive whenever the host has them. The on* subscriptions return an unsubscribe function — the view calls it on destroy(), which is how the IPC listeners do not leak across the view's many mount/unmount cycles.

Each write is fire-and-forget at the IPC layer: it returns { ok } immediately, and the actual plot comes back asynchronously on gnuplot:result, matched to its cell by the submission id the host echoes. This is why the view keeps a cellsById Map. The shell uses the identical invokesend split (`shellwritekillinbound,shellexit` outbound); gnuplot did not invent a new IPC discipline, only new channel names and a richer payload.

Lifecycle: spawn, mount, kill — and "hide, don't kill"

A gnuplot view has three distinct lifecycles that are easy to conflate and must be kept separate. Getting this wrong is the bug family that docs/VIEWS.md exists to prevent.

Spawn is lazy and tied to the first mount, not to creation. The Lisp command only creates a server-side record — a data-source carrying a fresh session id and a working directory; no process exists yet. The child is spawned the first time a window's <gnuplot-view> element actually binds the view record (spawned: false at that point):

function setBuffer(next) {
  buffer = next;
  // …
  if (!buffer.spawned && !buffer.ended && spawnFn) {
    buffer.spawned = true;            // latch so we spawn exactly once
    spawnFn(buffer.sessionId, { cwd: buffer.cwd })
      .then((result) => { /* on !ok, mark ended + disable input */ })
      .catch(() => { /* host's onExit surfaces not-installed/error */ });
  }
}

The spawned flag lives on the buffer record, not the element, precisely because the element is re-mounted as the user moves the tab around. If the latch lived on the element it would re-fire and spawn a second process.

Mount-moves hide, they do not kill. When a tab is dragged out of view, Godot moves the element to an off-screen "warehouse," firing disconnectedCallback. For a gnuplot view that callback is intentionally empty:

/** Hide-not-kill — the gnuplot process stays alive; only the DOM-tree
 *  position changed. A later `connectedCallback` finds `_inner` set
 *  and is a no-op. */
disconnectedCallback() {
  /* intentionally empty */
}

This is the single most important invariant the shell view established and the gnuplot view inherits: a view's process and transcript outlive its on-screen position. If you reaped the process on disconnectedCallback you would get a one-line "fix" that silently kills the user's session every time they look at another tab.

Only an explicit kill reaps the child. The process dies when the view is killed (C-x k) — the disposal path (disposeProcViewElement, covered in the wiring chapter) destroys the element and then routes through one central per-kind dispatch, disposeKindView in app.js:

function disposeKindView(view, context) {
  if (!view || typeof view.kind !== 'string') return;
  if (view.kind === 'shell')   { /* … window.host.shellKill(view.sessionId) … */ }
  if (view.kind === 'gnuplot') {
    if (typeof view.sessionId !== 'string') return;
    try {
      if (window.host && typeof window.host.gnuplotKill === 'function') {
        window.host.gnuplotKill(view.sessionId);
      }
    } catch { /* Process is already gone — nothing to do. */ }
    return;
  }
  // …
}

Keeping "free renderer memory" and "reap the OS process" as two different actions is what lets hide-not-kill work at all: unmounting must be cheap and reversible, while killing is final and explicit.

The Lisp surface: how the kind becomes reachable

A view kind that the host can build is useless until a user can summon it, and in Godot that last mile is Lisp, not host code — Lisp that executes in the spine, where the keymap and the command registry live. A gnuplot-mode with the label "Gnuplot" exists only to give the modeline something to show — its own comment notes the buffer "is shown through the L4 gnuplot view … not the editor view, so no text-buffer keymap applies." That a whole view kind is reachable, and rebindable, entirely from the stdlib Lisp — without recompiling the host — is the editor's extension story working as designed. (The wiring chapter walks through each piece.)

Driving gnuplot: the long-lived pipe and the SVG protocol

By this point we have a gnuplot-kind buffer and a custom element to display it. What we do not yet have is the hard part: a reliable conversation with an external program that was never designed to be embedded. gnuplot in pipe mode is a line-oriented REPL. It reads commands from stdin, writes print output to stdout and diagnostics to stderr, and — crucially — gives you no framing. There is no "command N finished" marker, no exit code per command, no length prefix on its output. It just talks until it has nothing more to say, and "nothing more to say" looks exactly like "still thinking."

The job of this layer is to impose a request/response discipline on a stream that has none, and to do it in a way that is testable without gnuplot even being installed. That last constraint shaped the whole design, so it is worth stating the split up front:

  • apps/desktop/src/gnuplot-protocol.js — pure, DOM-free, Electron-free logic: how to frame a submission, how to decide an SVG is real, and the stream demultiplexer that recognises when a submission is done. This is what the unit tests exercise.
  • apps/desktop/src/gnuplot.js — the host glue: one long-lived child per session, temp-file capture, IPC, and the not-installed degradation path. It uses the protocol module but contains none of its logic.

One process per session, strictly serialized

Each gnuplot buffer owns exactly one gnuplot child, spawned lazily on first mount and kept alive for the life of the buffer. We do not spawn a fresh gnuplot per command. That matters: gnuplot is stateful — sets, variables, and ranges accumulate across commands — and a notebook REPL is only useful if set xrange [0:10] still applies to the next plot. 

const child = spawn('gnuplot', [], {
  cwd,
  env,
  stdio: ['pipe', 'pipe', 'pipe'],
  detached: false,
});

Two details in the spawn are load-bearing. First, stdio is three plain pipes — no pseudo-terminal. gnuplot's pipe mode wants stdinstdoutstderr, not a tty, so unlike the shell view there is no PTY, no resize channel, and no native addon to build. Second, the environment:

// GNUTERM=unknown stops gnuplot trying to auto-select an interactive
// terminal (qt/x11/wxt) at startup. We set the real `svg` terminal per
// submission anyway.
const env = { ...process.env, GNUTERM: 'unknown' };

Submissions are strictly serialized. A user command is not written to stdin directly; it is pushed onto a per-session queue and a pump only starts the next job when the demultiplexer is idle:

function pump(sessionId) {
  const entry = sessions.get(sessionId);
  if (!entry || entry.dead) return;
  if (entry.demux.busy || entry.queue.length === 0) return;
  // ... shift the job, build sentinels, set demux.begin({ onComplete }),
  //     write the framed program to gnuplot's stdin ...
}

Serialization is what makes the framing tractable. Because gnuplot processes its stdin in order and we never have two submissions in flight, every byte that arrives on stdout/stderr unambiguously belongs to the one active submission.

The submission frame: preamble, user text, sentinel epilogue

Here is the heart of the protocol. Each user command is wrapped by buildSubmission into a small gnuplot program. The user's text goes in verbatim and unmodified in the middle; everything around it is framing we control. 

export function buildSubmission(params) {
  const {
    userText, tmpFile, sentinelOut, sentinelErr,
    width = 720, height = 480, theme = DEFAULT_THEME,
  } = params;
  const t = themeFor(theme);
  const term =
    `set terminal svg size ${width},${height} dynamic enhanced ` +
    `background rgb '${t.background}' font 'sans,11'`;
  return [
    term,
    `set output ${quoteGnuplot(tmpFile)}`,
    t.block,                          // dark theme palette / axis colours
    userText,                         // verbatim, unmodified
    'unset output',                   // flush + close the SVG (mandatory)
    "set print '-'",
    `print ${quoteGnuplot(sentinelOut)}`,        // "submission complete" -> stdout
    "set print '/dev/stderr'",
    `print ${quoteGnuplot(sentinelErr)}`,        // "stderr flushed"       -> stderr
    "set print '-'",
    '',                               // trailing newline
  ].join('\n');
}

Reading the sequence top to bottom, each line earns its place. set terminal svg re-declares the SVG generator on every submission — we don't trust the terminal to persist across commands. set output <tmpFile> redirects the plot bytes to a temp file rather than to stdout — the single most important design choice in the protocol, because routing the binary-ish plot to a file leaves stdoutstderr carrying only/ textual output and our sentinels. unset output is mandatory and a classic gnuplot footgun: gnuplot buffers the SVG, and the file is not complete (no closing </svg>) until the output is closed.

Sentinel framing: completion gated on BOTH streams

Since gnuplot won't tell us when a command is done, we make it tell us — by appending two print statements whose output we recognise. The tokens are deliberately long and unguessable so they can't collide with real user output:

export function sentinelsFor(id, nonce) {
  return {
    stdout: `__GODOT_GP_DONE__${id}__${nonce}__`,
    stderr: `__GODOT_GP_ERR__${id}__${nonce}__`,
  };
}

A private prefix, the submission id, and a fresh 6-byte random nonce per submission. The subtle part is why there are two sentinels, one per stream. gnuplot writes errors to stderr, which is a separate pipe from stdout, and the two are not synchronised — when the stdout sentinel arrives, there may still be error bytes in flight on stderr. So the epilogue prints a sentinel down each stream, and a submission is considered complete only when both sentinels have been observed.

One trap, verified against gnuplot 6. set print '-2' does not mean "fd 2" — gnuplot opens a file literally named "-2", so the stderr sentinel vanishes into that file and the submission hangs forever. The code uses set print '/dev/stderr' instead.

The demultiplexer: a pure reducer over byte chunks

Pipes deliver bytes in arbitrary chunks. A sentinel can be split across two data events; a single chunk can contain several lines. The SubmissionDemux absorbs all of that. It is a small line-buffered state machine with no DOM and no subprocess handle — which is exactly why it can be unit-tested against synthetic chunk sequences. 

pushStdout(chunk) {
  this._outBuf += chunk;
  let nl;
  while ((nl = this._outBuf.indexOf('\n')) !== -1) {
    const line = this._outBuf.slice(0, nl);
    this._outBuf = this._outBuf.slice(nl + 1);
    const a = this._active;
    if (a && line === a.sentinelOut) {
      a.gotOut = true;
      this._maybeFinish();
    } else if (a) {
      a.stdoutLines.push(line);          // real user output
    }
  }
}

It only acts on complete lines (terminated by \n); a trailing partial line stays in _outBuf until the rest arrives. That is what makes a split sentinel safe. Completion is gated on both flags:

_maybeFinish() {
  const a = this._active;
  if (!a || !a.gotOut || !a.gotErr) return;   // need BOTH sentinels
  this._active = null;
  a.onComplete({
    stdout: a.stdoutLines.join('\n'),
    stderr: a.stderrLines.join('\n'),
  });
}

Capturing the SVG temp file vs. text and errors

When both sentinels land, the demux fires its onComplete, which the host wired to finishSubmission. Now the host turns three independent channels — the temp file, stdout text, stderr text — into one result payload. Note that the SVG never travelled over a pipe; it was written to disk, and we read it back here:

function finishSubmission(sessionId, id, tmpFile, stdout, stderr) {
  const entry = sessions.get(sessionId);

  let svg = null;
  try {
    const st = statSync(tmpFile);
    const text = readFileSync(tmpFile, 'utf8');
    if (svgHasPlot(st, text)) {
      // Strip any <script> gnuplot's svg terminal might emit, as
      // defence-in-depth before the renderer inlines the markup.
      svg = stripScripts(text);
    }
  } catch {
    // No file -> no plot. Leave svg null.
  }
  // Read-and-delete: the SVG bytes now live in the result payload.
  unlink(tmpFile, () => {});

  if (entry) entry.active = null;
  if (entry && !entry.sender.isDestroyed()) {
    entry.sender.send('gnuplot:result', {
      sessionId, id, svg, text: stdout, error: stderr,
    });
  }
  pump(sessionId);   // start the next queued submission
}

A command need not produce a plot. print "hi" writes to stdout and never opens an output file; set xrange [0:10] produces nothing at all. So svg is null unless a real plot file exists. "Real plot" is a heuristic, not a guess — svgHasPlot rejects a file that's too small, that lacks a closing tag (truncated), or that has no drawn element: 

export function svgHasPlot(stat, text) {
  if (!stat || typeof stat.size !== 'number') return false;
  if (stat.size <= EMPTY_SVG_THRESHOLD) return false;            // 512 bytes
  if (typeof text !== 'string') return false;
  if (!text.includes('</svg>')) return false;                    // not truncated
  return /<(path|rect|polyline|circle|image|use|text)\b/.test(text);  // drawn
}

Interrupting a running plot

A heavy plot (a fine samples count over a slow function) can take real time. Pressing C-c in the input line sends SIGINT to the child:

function signalSession(sessionId) {
  const entry = sessions.get(sessionId);
  if (!entry || entry.dead) return false;
  try {
    return entry.child.kill('SIGINT');   // already-queued epilogue then runs
  } catch {
    return false;
  }
}

Because the epilogue (unset output plus the two sentinel prints) is already queued in gnuplot's stdin, an interrupted plot still drives both sentinels and the cell completes cleanly — usually as an error or empty cell rather than a plot — instead of leaving a pending cell stuck forever. The interrupt cooperates with the framing rather than bypassing it.

The session and history data model

Everything the gnuplot view shows on screen is reconstructed from three small, deliberately boring data structures: the cell (one submitted command and its eventual result), the command-history ring (the Up/Down recall buffer behind the input line), and the per-session submission queue that lives in the host. None of these is a framework abstraction. They are plain objects, a Map, and an array, and that plainness is the point.

A cell is the unit of the transcript

The shell view streams raw pty bytes into an xterm grid; there is no notion of a "result" there, just an ever-scrolling character buffer. gnuplot is different: each command you submit produces one result — a plot, or some text, or an error. So the gnuplot view's transcript is not a character stream but a column of discrete cells, each created the instant you press Enter and filled in later when the host answers.

A cell is a tiny state machine. It is created pending, then onResult resolves it into exactly one terminal shape based on which of svg text error the payload carries — and a cell may carry several of these at once (a plot and a warning). The CSS classes name the states directly:

State (CSS class) Set when What the cell shows
gnuplot-cell-pending Cell created, awaiting the result Just the echoed command, dimmed (opacity: 0.7)
gnuplot-cell-plot payload.svg is a non-empty string The themed SVG, inlined and scaled to the cell
gnuplot-cell-stdout payload.text is non-blank print / show output, foreground colour
gnuplot-cell-warn payload.error is non-blank and a plot was produced The stderr text as a muted warning under the plot
gnuplot-cell-error / -stderr payload.error is non-blank and there is no plot Red text, red cell border (a typo, a real failure)
gnuplot-cell-empty None of the above produced output A dim italic (no output) placeholder

The resolution logic in onResult reads almost like the table — it inspects the payload field by field, appends a region for each, and falls back to an explicit empty acknowledgement so a bare set command never leaves a blank cell:

function onResult(payload) {
  if (!payload || typeof payload !== 'object') return;
  if (!buffer || payload.sessionId !== buffer.sessionId) return;
  const cell = cellsById.get(payload.id);
  if (!cell) return;
  cellsById.delete(payload.id);
  cell.classList.remove('gnuplot-cell-pending');

  let rendered = false;
  let hasPlot = false;
  // The plot, if any. The SVG is trusted-local (generated by the
  // host's own gnuplot, scripts already stripped main-side); inline it
  // so it scales with the cell.
  if (typeof payload.svg === 'string' && payload.svg !== '') {
    const plot = doc.createElement('div');
    plot.className = 'gnuplot-cell-plot';
    plot.innerHTML = payload.svg;
    attachPlotMenu(plot, payload.svg, payload.id);   // right-click: save / copy
    cell.append(plot);
    rendered = true;
    hasPlot = true;
    // Record the plot (persistently) + notify the minimap so it can add
    // a thumbnail. The cell ref lets scrollToPlot() jump the transcript.
    plots.push({ id: payload.id, svg: payload.svg, cell });
    notifyPlots();
  }
  // Text output (print, show, ...).
  if (typeof payload.text === 'string' && payload.text.trim() !== '') {
    appendRegion(cell, 'gnuplot-cell-stdout', payload.text);
    rendered = true;
  }
  // Anything on stderr. When a plot WAS produced, the command succeeded
  // and stderr is just a non-fatal notice — show that as a muted
  // warning, not a red error; only stderr with no plot is a real failure.
  if (typeof payload.error === 'string' && payload.error.trim() !== '') {
    if (hasPlot) {
      appendRegion(cell, 'gnuplot-cell-warn', payload.error);
    } else {
      cell.classList.add('gnuplot-cell-error');
      appendRegion(cell, 'gnuplot-cell-stderr', payload.error);
    }
    rendered = true;
  }
  // A bare `set` with no output: show a dim acknowledgement.
  if (!rendered) {
    appendRegion(cell, 'gnuplot-cell-empty', '(no output)');
  }
  scrollToEnd();
}

Notice that the three result fields are checked independently, not as a switch. A submission like plot sin(x) that also emits a warning will produce a cell that is both a plot and a warning — and stderr is only styled as a red error when no plot was produced. When a plot exists the command clearly succeeded, and gnuplot's notice (e.g. "Warning: empty y range … adjusting" when you plot a flat line) renders as a muted aside instead. The cellsById.delete(payload.id) at the top is what makes a cell single-shot: once resolved, its id is gone, and a duplicate result for the same id is silently dropped.

Why key by id at all, if submissions are serialized? The host runs one gnuplot child per session and processes submissions strictly in order, so results do arrive in order. Keying by id is belt-and-suspenders: it makes the renderer correct regardless of arrival order, and a stray or duplicate result simply finds no cell (if (!cell) return;) instead of corrupting the transcript. Robustness for the cost of one Map.

The command-history ring

The input line is a plain <input>. It has no readline, no ZLE, nothing that gives a shell its Up/Down recall. The shell view doesn't need to care — xterm.js hands raw bytes to the child shell, whose own readline owns the arrow keys. The gnuplot view has no such luxury, so it implements history itself, as a small DOM-free module that can be unit-tested without a browser. The model is the standard REPL triple — a list of entries, a cursor, and a stashed draft:

export function createHistory() {
  /** @type {string[]} */
  const entries = [];
  let index = 0;
  let draft = '';

  return {
    push(command) {
      if (typeof command === 'string' && command.trim() !== '') {
        entries.push(command);
      }
      index = entries.length;
      draft = '';
    },

    up(current) {
      if (entries.length === 0) return current;
      if (index === entries.length) draft = current;
      if (index > 0) index -= 1;
      return entries[index];
    },

    down(current) {
      if (index >= entries.length) return draft;
      index += 1;
      if (index === entries.length) return draft;
      return entries[index];
    },

    reset() { index = entries.length; draft = ''; },
    entries() { return entries.slice(); },
    index() { return index; },
  };
}

The cursor invariant is the whole trick: index === entries.length means "you are on the live, not-yet-submitted line." Stepping up from the live line first stashes whatever you had half-typed into draft, then walks the cursor toward older entries, clamping at the oldest. Stepping down walks back toward newer entries, and when it passes the newest it restores the stashed draft rather than blanking the input.

The draft is what separates this from a naive history. Without it, arrowing up mid-type and then back down would silently destroy the line you were writing. The up guard if (index === entries.length) draft = current captures it on the first step only. The ring's own unit suite covers pushupdown, draft excursions, blank-skip, cursor reset, and that entries() hands back a copy that can't mutate internal state.

How a submission flows through

With the cell and the ring in place, a single Enter keypress threads a whole round trip. On the host side, a write does not run gnuplot directly — it appends to a per-session queue and pumps it. This is where serialization is enforced:

function writeToSession(sessionId, data) {
  const entry = sessions.get(sessionId);
  if (!entry || entry.dead) return false;
  entry.counter += 1;
  entry.queue.push({ id: entry.counter, userText: String(data) });
  pump(sessionId);
  return true;
}

The host's counter is the source of truth for the id; the renderer's buffer.submitCounter shadows it so the two agree without a round trip. That message — { sessionId, id, svg, text, error } — is the seam between the two halves of the model. The host built it by demultiplexing a byte stream; the renderer consumes it in onResult, matches id back to the pending cell, and resolves the cell into its final state. Small enough to reason about in one line, rich enough to express every cell state.

Sessions, not a global. Each gnuplot command opens a fresh view with its own sessionId — minted by the server and equal to the data-source id, so it is stable and server-owned — and the host keys its sessions Map by that id. The view's onResult/onExit handlers both guard on payload.sessionId !== buffer.sessionId, so two open gnuplot views never cross-talk even though they share the same IPC channel.

The view element: a notebook over a long-lived gnuplot child

Everything up to here has been plumbing: the host spawns one gnuplot per session, frames each submission, and sends back a single gnuplot:result carrying { id, svg, text, error }. The view element is where that becomes something a person looks at. Its whole job is to turn a stream of those results into a scrolling notebook transcript: you type a command at the bottom, press Enter, and a cell appears above holding the rendered plot, any text output, or a red error.

The file is packages/renderer/src/gnuplot-view.js. It follows the same two-layer shape every non-text view in Godot uses — a plain createGnuplotView(container, options) factory that builds the DOM and wires the behaviour, wrapped by a GnuplotView extends ViewElement custom element that gives it the hide-not-kill lifecycle.

The DOM skeleton

The factory builds the three regions once, at construction time. Note the deliberate ordering in the flex column — header, transcript, input row — and that the transcript is the only one allowed to grow and scroll:

Filling the cell: text and errors

Text and error regions go through a tiny shared helper, which is the only place a <pre> is created. Using textContent (never innerHTML) for text and errors means gnuplot's output can never inject markup — only the trusted SVG path uses innerHTML: 

/** Append a text region to a cell, returning the created element. */
function appendRegion(cell, className, text) {
  const pre = doc.createElement('pre');
  pre.className = className;
  pre.textContent = text;
  cell.append(pre);
  return pre;
}

A notebook REPL wants the newest cell visible. The view does not track scroll position — it simply calls scrollToEnd after every mutation that adds height:

/** Scroll the transcript to the bottom. */
function scrollToEnd() {
  transcriptEl.scrollTop = transcriptEl.scrollHeight;
}

This works because the CSS makes the transcript the only scrollable region. The flex column gives the transcript flex: 1 1 auto and the crucial min-height: 0, so it shrinks to fit and scrolls internally while the header and input row stay pinned.

Exporting a plot: save and copy

A themed plot is worth keeping, so every plot cell carries a small context menu — attachPlotMenu hangs it off the plot <div> at render time. Two items: Save plot as… routes the SVG string through the factory's exportSvg (→ gnuplot:save-svg, whose handler lives with the other native-dialog code in files.js and writes wherever the save dialog says); Copy SVG puts the same string on the clipboard. 

/** Right-click a plot for a menu: save the SVG to a file, or copy it. */
function attachPlotMenu(plot, svg, id) {
  plot.addEventListener('contextmenu', (event) => {
    event.preventDefault();
    openMenu(event.clientX, event.clientY, [
      {
        label: 'Save plot as…',
        run: () => {
          if (exportSvg) exportSvg(svgWithIntrinsicSize(svg), `plot-${id}.svg`);
        },
      },
      {
        label: 'Copy SVG',
        run: () => {
          const clip = win && win.navigator && win.navigator.clipboard;
          if (clip) clip.writeText(svgWithIntrinsicSize(svg)).catch(() => {});
        },
      },
    ]);
  });
}

The svgWithIntrinsicSize wrapper is the interesting detail, and it is the third pure module of the feature (packages/renderer/src/gnuplot-svg.js). gnuplot's dynamic svg terminal emits a viewBox but no width/height — ideal for scaling to its container when inlined in a cell, but it leaves the exported file with no intrinsic size, which standalone SVG viewers rely on for their zoom and fit controls. The function injects explicit pixel width and height derived from the viewBox onto the root element (a no-op when both are already present, or when there is no usable viewBox), so a saved or copied plot is a proper, self-contained image. Being pure string surgery with no DOM, it has its own node:test suite.

The minimap: a thumbnail per plot

Godot's minimap (C-x m) is a companion pane, and for a gnuplot view it does something better than shrunken text: it draws a clickable thumbnail per plot. The view keeps a persistent plots array — { id, svg, cell }, appended in onResult and surviving after cellsById forgets the id — and exposes three methods on the element for the minimap to consume: 

/** The rendered plots in document order: `[{ id, svg }]` — the minimap

The input line, history, and chord forwarding

The view wires the history ring to the input's keydown handler, which is also where the chord-forwarding and the C-c interrupt live. Enter and the arrows are handled locally; a key that looks like an editor chord is forwarded to the keymap:

input.addEventListener('keydown', (event) => {
  if (event.key === 'Enter') {
    event.preventDefault();
    const cmd = input.value;
    if (cmd.trim() !== '') {
      history.push(cmd);
      runCommand(cmd);
    }
    input.value = '';
    history.reset();
    return;
  }
  if (event.key === 'ArrowUp') {
    event.preventDefault();
    input.value = history.up(input.value);
    win.requestAnimationFrame(() => {
      input.setSelectionRange(input.value.length, input.value.length);
    });
    return;
  }
  if (event.key === 'ArrowDown') { /* …mirror of ArrowUp… */ }

  // C-c interrupts a running plot (the shell-view analog of SIGINT) —
  // but only at rest. Mid-chord, this C-c is the continuation of a
  // sequence (e.g. C-x C-c = quit), so it must fall through to the
  // forwarding block below rather than be swallowed as an interrupt.
  if (
    !chordPending() &&
    event.key === 'c' && event.ctrlKey &&
    !event.metaKey && !event.altKey
  ) {
    if (buffer && signalFn && !buffer.ended) {
      event.preventDefault();
      signalFn(buffer.sessionId);
      return;
    }
  }
  // Forward editor chords (C-x b, M-x, …) to the host keymap — but ONLY
  // keys held with Ctrl or Alt, the Emacs chord modifiers. Plain typing,
  // Backspace, the arrows, Shift, and Cmd-based edits (⌘A/⌘C/⌘V) stay in
  // the input as native text editing.
  const bareModifier =
    event.key === 'Shift' || event.key === 'Control' ||
    event.key === 'Alt' || event.key === 'Meta';
  if (
    onKey && !bareModifier &&
    (chordPending() || event.ctrlKey || event.altKey)
  ) {
    const key = keyEventToString(event);
    if (key && onKey(key)) event.preventDefault();
  }
});

The last branch is the bridge back to the editor: because the input is a real focusable <input>, the editor keymap would otherwise go dark while you're typing in it. Forwarding chords through onKey — which, under the server architecture, routes the key string to the spine's keymap — keeps C-x b, M-x, and friends alive; exactly the trick the browser view uses for its URL bar. The forwarding is deliberately narrow: only keys carrying Ctrl or Alt (the Emacs chord modifiers) leave the input, so plain typing, Backspace, and Cmd-based edits (⌘A⌘C⌘V) remain native text editing — forwarding a plain key would route it to handle-key, which would try to self-insert into a text buffer this non-text view doesn't have. The chordPending() calls are the mid-chord seam: they let a prefix continuation without modifiers (the 3 of C-x 3) be forwarded, and stop C-c from being eaten as an interrupt when it is really the tail of C-x C-c. Enter and the arrows are handled locally and deliberately not forwarded.

Theming is a deliberate no-op

Godot's other non-text views recompute colours when the editor theme changes — the shell view re-reads CSS variables and pushes them into xterm. The gnuplot view is the interesting exception: its applyTheme is a deliberate no-op. (Don't confuse this with the plot themes of the previous chapter — those are a per-session, host-side property of the SVG output, driven by the header picker, not by the editor's theme.)

/** Re-theme. The plot SVGs bake their own dark background at render
 *  time, so there's nothing to recompute here; kept for parity with
 *  the singleton view interface. */
function applyTheme() {
  /* no-op — SVGs are self-themed at render time */
}

The theme of a plot is not applied by the renderer at all — it is baked into the SVG by the host at render time. The method still exists, empty, so the view satisfies the same { setBuffer, focus, applyTheme, destroy } interface as every other view element and can be registered uniformly. One consequence worth flagging: a live theme switch — editor theme or plot theme — will not re-colour plots already in the transcript; only newly rendered cells pick up the new palette.

The custom-element wrapper and lifecycle

The factory knows nothing about being mounted, hidden, or moved between panes. That is the custom element's job. GnuplotView extends ViewElement is a thin adapter: configure(options) stashes the IPC wiring before mount, connectedCallback lazily builds the inner factory on first attach, and — the important bit — disconnectedCallback is intentionally empty: 

export class GnuplotView extends ViewElement {
  get kind() { return 'gnuplot'; }

  connectedCallback() {
    if (this._inner !== null) return;
    this._inner = createGnuplotView(this, this._options ?? {});
    if (this._pendingBuffer !== null) this._inner.setBuffer(this._pendingBuffer);
  }

  /** Hide-not-kill — the gnuplot process stays alive; only the DOM-tree
   *  position changed. A later `connectedCallback` finds `_inner` set
   *  and is a no-op. */
  disconnectedCallback() {
    /* intentionally empty */
  }

  /** Explicit teardown: drop the IPC subscriptions. The host's
   *  kill-view path reaps the gnuplot process separately. */
  destroy() {
    if (this._inner !== null) { this._inner.destroy(); this._inner = null; }
    this._pendingBuffer = null;
  }
}

Hide-not-kill is the whole point of the empty disconnectedCallback. Moving a pane to the warehouse, or splitting and rearranging panes, fires disconnectedCallback on the element. If that tore down the view, the user would come back to an empty transcript and a fresh gnuplot process — their plots gone. So disconnect does nothing, and a later connectedCallback finds _inner already set and short-circuits. The gnuplot process is only reaped on explicit destroy() plus the host-side kill path. This split is the rule documented in docs/VIEWS.md: the DOM position is owned by the pane tree, the process lifetime is owned by the host, and the two are deliberately decoupled.

Command history and recall

Every REPL needs a way to bring back what you just typed. You run plot sin(x), eyeball the curve, then want plot sin(x), cos(x) — and you do not want to retype the whole line. The fix is the same one every shell and language REPL has shipped for decades: Up walks backward through the commands you submitted, Down walks forward again, and whatever the arrows land on is dropped into the input where you can edit it and re-run it.

The interesting question for the gnuplot view is not whether to have history — it is who owns it.

Why this view has to implement history itself

Godot already has a terminal view (shell v4), and it has full command history — Up/Down, reverse-search, the lot. But none of that history code lives in Godot. The shell view is an xterm.js grid that forwards raw keystrokes straight to a child shell; the shell's own readline/ZLE line editor owns the history ring. Godot is just a dumb pipe in both directions. It never sees a "command" — only bytes.

The gnuplot view is the opposite shape. Its input line is a plain <input> element, and gnuplot's own command line does not run inside it. There is no readline in the loop to remember anything. So if this view is going to have Up/Down recall, the view has to keep the ring itself. The file header states exactly this: 

/**
 * @file A small, DOM-free command-history ring for the gnuplot notebook
 * view's input line. The shell v4 view keeps no history of its own —
 * xterm.js hands raw bytes to the child shell, whose readline/ZLE owns
 * Up/Down. The gnuplot view has a bare `<input>` with no readline, so it
 * must implement history itself. Extracting it as pure logic keeps it
 * unit-testable without a DOM (per CLAUDE.md's "unit-test pure logic").
 */

The Godot pattern. Where a child process owns the line editor, forward bytes and keep no state. Where Godot owns the input element, Godot owns the history. The browser view's URL bar follows the same rule. This file is the gnuplot view paying the price of owning its input — but it pays it in twelve lines of pure logic, not a re-implemented line editor.

The cursor model

The live line is a real position one past the newest entry; that is where draft lives.

up and down: the recall logic

The two arrow methods take the input's current text as an argument. That is deliberate — it is how the draft gets captured at the exact moment you leave the live line, without the history needing any reference to the DOM.

up(current) {
  if (entries.length === 0) return current;
  if (index === entries.length) draft = current;
  if (index > 0) index -= 1;
  return entries[index];
},

down(current) {
  if (index >= entries.length) return draft;
  index += 1;
  if (index === entries.length) return draft;
  return entries[index];
},

Reading up line by line: if (entries.length === 0) return current — Up on an empty history is a no-op. if (index === entries.length) draft = current — this fires only on the first Up from the live line; step Up again from inside history and this is false, so an earlier-stashed draft is never clobbered. if (index > 0) index -= 1 — walk one step older, but clamp at the oldest entry. down is the mirror image; its subtlety is the live line — stepping forward past the newest entry lands you back on the live line and hands back the draft you stashed.

Why a separate, DOM-free module

The ring could have lived as three closure variables inside createGnuplotView. Pulling it out into gnuplot-history.js buys one concrete thing: it is testable with no browser, no jsdom, no custom element. The whole behaviour — including the fiddly bits people get wrong — is nailed down by a node:test suite that imports the function directly:

test('down walks back toward the live line and restores the stashed draft', () => {
  const h = createHistory();
  h.push('first');
  h.push('second');
  // Start typing a new line, then arrow up — the draft is stashed.
  assert.equal(h.up('half-typed'), 'second');
  assert.equal(h.up('half-typed'), 'first');
  // Walk back down: second, then the live line (the draft).
  assert.equal(h.down('first'), 'second');
  assert.equal(h.down('second'), 'half-typed');
});

test('entries returns a copy that cannot mutate internal state', () => {
  const h = createHistory();
  h.push('a');
  const snapshot = h.entries();
  snapshot.push('hacked');
  assert.deepEqual(h.entries(), ['a']);
});

Design takeaway for Godot. When a view owns its own input element, the line-editing logic is yours to write — but keep it DOM-free and pure. The element stays a thin adapter (read input.value, write input.value, park the caret); the behaviour lives where it can be tested in milliseconds without a render. The same split is why the protocol framing and the svgHasPlot check are their own pure modules too.

Wiring the view kind into Godot

By this point the two halves exist in isolation: a main-process host (apps/desktop/src/gnuplot.js) that spawns and drives a gnuplot child, and a renderer custom element (packages/renderer/src/gnuplot-view.js) that draws the notebook. Neither knows about the other, and neither is reachable from inside the editor. Wiring is the seam that joins them: it makes gnuplot a first-class view kind alongside text, image, shell, and the rest.

There is no plugin manifest and no registry to append to. In Godot a view kind is wired by touching a fixed set of seams, each of which answers one question the shell asks at a different moment.

The Lisp surface: command, keymap, mode

The user-facing entry point is a Lisp command. It is deliberately thin — it documents the feature and delegates to a single primitive.

(defcommand gnuplot ()
  "Open a fresh gnuplot buffer.
   ...
   Each call to `gnuplot` creates a new buffer — switch back to an open
   one by name with `C-x b`. If gnuplot is not installed, the view shows
   install instructions (`brew install gnuplot`)."
  (open-gnuplot-buffer!))

The keybinding lives under the C-c prefix map. Note the binding is to the symbol 'gnuplot, not to the procedure value — so load order between the keymap and the command definition doesn't matter; the symbol resolves at dispatch time. A gnuplot-mode (in modes.lisp) gives the buffer a modeline label — the view has no text buffer, so this is cosmetic: 

;; The gnuplot mode — a `gnuplot`-kind buffer is shown through the L4
;; gnuplot view (a notebook REPL), not the editor view, so no text-buffer
;; keymap applies. The mode exists for the modeline label only.
(define-mode gnuplot-mode
  :name "Gnuplot")

One trap worth naming: gnuplot.lisp must be added to both stdlib load lists — STDLIB_FILES in packages/stdlib/src/index.js (what the unit tests and tooling load) and SPINE_STDLIB in spine.js (what the live server actually loads). There is no single source of truth; a file present in the first list but missing from the second produces a command that passes every test and does not exist in the running editor.

A regression test in packages/stdlib/test/stdlib.test.js pins all three facts at once — the command loads, it is documented, and C-c g resolves to it: (procedure? gnuplot) is true, (doc gnuplot) is a string, and (eq? (get c-c-keymap "g") (quote gnuplot)) holds.

The primitive: open-gnuplot-buffer!

The Lisp command calls one host primitive — registered in spine.js, because that is where the Lisp world runs. It is one line:

'open-gnuplot-buffer!': () => openProcessView('gnuplot'),

openProcessView is the shared open path for both live-process kinds (the shell uses the same function with 'shell'). Its job is to mint a server-owned 'gnuplot' data-source, resolve a working directory, and switch the active client's focused leaf to the new view. Crucially, it does not spawn the process — that happens when a window's element first binds the view. 

function openProcessView(kind) {
  procSeq[kind] = (procSeq[kind] ?? 0) + 1;
  const n = procSeq[kind];
  const cwd = activeEntry && activeEntry.filePath
    ? dirname(activeEntry.filePath)
    : '';
  const name = n === 1 ? procLabel(kind) : `${procLabel(kind)}<${n}>`;
  const src = dataSources.add({ kind, name, state: { cwd } });
  // sessionId is tied to the (unique) data-source id so it's stable +
  // server-owned; the renderer keys MAIN's gnuplot:* IPC by it. The
  // server itself never touches the process.
  src.state.sessionId = src.id;
  switchClientToSource(activeClientIndex, src.id);
  return src.id;
}

Two server-side decisions do real work here. The session id is not a fresh random token — it is the data-source id, which makes it stable, unique, and owned by the same authority that owns the view's existence. And the cwd is resolved at open time, server-side, to the directory of the active document — so plot 'data.dat' finds the file next to whatever you were editing (an empty cwd makes the main-process host fall back to $HOME). (A nextGnuplotSessionId counter-plus-timestamp generator survives in app.js, but only on a legacy view-clone path; the open path never touches it.)

Per-instance elements: several sessions at once

Some of Godot's view kinds are mounted as a single custom-element instance — a singleton created once at startup and moved between panes by show/hide. The live-process kinds are deliberately not like that. A gnuplot session's whole value is its accumulated state (the transcript, the sets, the running child), and you routinely want two of them visible at once — one in each half of a split, or as tabs in a tabline. So in the shipped architecture each 'gnuplot' (or 'shell') data-source owns its own <gnuplot-view> element and its own child process: 

const PROC_VIEW_KINDS = new Set(['shell', 'gnuplot']);

/** The per-instance element for a live-process VIEW (shell/gnuplot) —
 *  created (configured + mounted in PANE-EL) on first use, then reused
 *  and re-parented. */
function ensureProcViewElement(view, paneEl) {
  let el = procViewElementByView.get(view);
  if (el) {
    // Reuse: re-parent only. Do NOT call setBuffer again — the element
    // is already bound and its child is live. Re-parenting (a DOM move)
    // fires only the no-op disconnected/connected callbacks.
    if (paneEl && el.parentNode !== paneEl) paneEl.append(el);
    return el;
  }
  const factory = perKindConfigureFactory(view.kind);
  el = document.createElement(`${view.kind}-view`);
  if (factory) el.configure(factory());
  el.setBuffer(view); // first bind: spawns the child lazily
  if (paneEl) paneEl.append(el);
  procViewElementByView.set(view, el);
  return el;
}

The recipe for each fresh instance comes from perKindConfigureFactory — the same configureGnuplotView factory as ever, called once per element so each <gnuplot-view> gets its own freshly-bound callbacks and its own session: 

function perKindConfigureFactory(kind) {
  switch (kind) {
    // ...
    case 'shell':             return configureShellView;
    case 'gnuplot':           return configureGnuplotView;
    default:                  return null;
  }
}

Two details in ensureProcViewElement are load-bearing. The reuse branch re-parents and nothing else — a process leaf re-mounts on every pane reconcile, and a redundant setBuffer would re-enter the element's async build and double-spawn the child; a plain DOM move fires only the no-op disconnected/connected callbacks, which is exactly what hide-not-kill wants. And the procViewElementByView map is keyed by the view record, not the pane — so the element (and its live transcript) follows the view wherever the layout puts it.

Kill on close

Killing the view routes through disposeProcViewElement, the mirror of the mount path — it destroys the renderer element (dropping the IPC subscriptions) and separately reaps the OS process:

function disposeProcViewElement(view) {
  const el = procViewElementByView.get(view);
  if (!el) return;
  try { el.destroy(); } catch { /* already gone */ } // view + IPC unsubscribe
  el.remove();
  procViewElementByView.delete(view);
  // Reap the child in MAIN (the renderer-side destroy() does NOT kill it).
  try { disposeKindView(view); } catch { /* process already gone */ }
}

disposeKindView is the per-kind dispatch that sends gnuplotKill over the bridge. On the host side gnuplot:kill lands in terminateSession, which SIGTERMs the child, rm -rfs the per-session temp dir, and forgets the entry. The contract is closed in both directions: every spawn on first bind has a matching kill on close, keyed by the session id that the spine minted and that travelled untouched through the view record the whole way.

Workspace persistence: the arrangement, not the process

Because the data-source lives in the server, a gnuplot view participates in session/workspace save like any other leaf. What gets persisted is deliberately minimal — the arrangement, never the live process:

// serialising a layout (spine.js):
if (ds.kind === 'shell' || ds.kind === 'gnuplot') {
  return { kind: ds.kind, cwd: ds.state?.cwd ?? '' };
}

On restore, restoreProcessView(kind, cwd) mints a fresh data-source (a new session id, and — once a window binds it — a new child) in the saved working directory, and the restored leaf points at it. Your pane shape and the "a gnuplot lives here, working in that directory" fact survive a relaunch; the transcript and the child's accumulated set state do not. That is the honest contract for a live process, and it is the same one the shell and browser views use.

The seams, in one list

For a future view kind, this is the checklist the gnuplot wiring instantiates — each item answers a question the system asks at a specific moment. (The condensed, kind-agnostic version of this list lives in docs/CUSTOM-VIEWS.md; the dispatch side is docs/MODEL-B-DISPATCH.md.)

  • preload bridge — how does the renderer reach the host? (gnuplotSpawn/Write/Signal/Kill/SaveSvg/SetTheme, onGnuplotResult/Exit)
  • configure factory — how is a view instance handed its host callbacks? (configureGnuplotView)
  • per-instance element — what shows this kind, and how is it reused across re-mounts without a double-spawn? (PROC_VIEW_KINDS, ensureProcViewElement)
  • perKindConfigureFactory — how does each fresh instance get its recipe?
  • spine primitive + stdlib entry — how does Lisp create a view of this kind, and does the file load in the server? (open-gnuplot-buffer! → openProcessView; gnuplot.lisp in both STDLIB_FILES and SPINE_STDLIB)
  • command + keymap + mode — what does the user type? (gnuplot, C-c g, gnuplot-mode)
  • spawn on first bind — flag-gated in setBuffer.
  • kill on close — disposeProcViewElement → disposeKindView.
  • workspace persistence — what survives a relaunch? (the serialize/restore live-process branches: kind + cwd, fresh child)

Miss any one and the failure is specific and visible: skip the SPINE_STDLIB entry and the command passes its tests but does not exist in the running editor; skip the dispose path and processes leak; skip the reuse-only re-parent and a pane reconcile double-spawns the child.

Testing, graceful degradation, and where to take it next

A subprocess-driven view is mostly untestable in a unit test if you write it naively: spawning a real gnuplot, waiting on async IPC, diffing rendered SVG bytes — none of that runs under a plain node --test. So the design question that governs this whole feature is: how much of it can be made pure? The more logic that lives in DOM-free, Electron-free, subprocess-free functions, the more of it a fast test suite pins down, and the smaller the residue that genuinely needs a human at a running app.

The pure/live split, by design

Everything that can be reasoned about without a live subprocess was pulled out of the host module (gnuplot.js, which holds Electron and child_process and is not unit-tested) into a sibling that imports nothing but JavaScript: apps/desktop/src/gnuplot-protocol.js — the framing, the themes, the SVG-has-plot heuristic, the demux. The same move happens twice on the renderer side: the command-history ring is lifted into packages/renderer/src/gnuplot-history.js as a createHistory() factory with no DOM dependency at all, and the export sizing into packages/renderer/src/gnuplot-svg.js as pure string surgery.

What the pure assertions pin down

The three suites — protocol, history, and export sizing — cover the parts that are easy to get subtly wrong. Quoting is one: the temp-file path is interpolated into set output '…', and gnuplot's single-quoted strings do not interpret backslashes, so the safe escape is to double embedded single quotes and otherwise pass bytes through verbatim — which means a Windows-style path with backslashes must survive untouched:

test('quoteGnuplot single-quotes and doubles embedded quotes', () => {
  assert.equal(quoteGnuplot('/tmp/a.svg'), "'/tmp/a.svg'");
  assert.equal(quoteGnuplot("o'brien"), "'o''brien'");
  assert.equal(quoteGnuplot(''), "''");
});

test('quoteGnuplot does not interpret backslashes (gnuplot single-quote semantics)', () => {
  // A Windows-ish path with backslashes survives verbatim.
  assert.equal(quoteGnuplot('C:\\tmp\\a.svg'), "'C:\\tmp\\a.svg'");
});

The both-sentinels gate is the heart of the framing protocol: a submission is "done" only when both the stdout and the stderr sentinel have arrived. The test asserts the demux waits, and that a sentinel cut across a chunk boundary still reassembles:

demux.pushStdout('hello\nworld\n');
demux.pushStdout('OUT\n'); // stdout sentinel — but stderr not yet in
assert.equal(result, null, 'must wait for BOTH sentinels');
demux.pushStderr('ERR\n');
assert.deepEqual(result, { stdout: 'hello\nworld', stderr: '' });
assert.equal(demux.busy, false);

The gnuplot-not-installed path

gnuplot is genuinely often missing, and the design choice is to make that a first-class outcome, not an error in the transcript. The tricky part is that spawn('gnuplot', …) does not throw synchronously for a missing binary — it resolves, then emits an async error event a tick later with code === 'ENOENT'. So the spawn IPC handler returns { ok: true } immediately and the not-installed signal arrives separately: 

child.on('error', (error) => {
  entry.dead = true;
  sessions.delete(sessionId);
  rm(tmpDir, { recursive: true, force: true }, () => {});
  if (sender.isDestroyed()) return;
  if (error.code === 'ENOENT') {
    sender.send('gnuplot:exit', {
      sessionId, code: null, signal: null,
      notInstalled: true,
      message: NOT_INSTALLED_MESSAGE,
    });
    return;
  }
  sender.send('gnuplot:exit', {
    sessionId, code: null, signal: null,
    error: error.message,
    message: `gnuplot failed to start: ${error.message}`,
  });
});

The renderer's exit handler keys on the notInstalled flag, replaces the transcript with a centred install card, and disables the input — there is no point letting the user type at a process that will never answer. The host owns the canonical message (with brew install gnuplot and the Debian/Ubuntu line), and the renderer carries an identical DEFAULT_NOT_INSTALLED fallback.

Defence in depth on the SVG. Adjacent to degradation is a second safety property: gnuplot's svg terminal can emit a <script> (its interactive mousing layer). The host strips it before the renderer inlines the markup — svg.replace(/<script\b[\s\S]*?<\/script>/gi, '') — so even though the SVG is trusted-local it never reaches the DOM with executable content. The same strip is applied to every plot embedded in this very page.

Where to take it next

The architecture leaves natural extensions cheap to add, because the hard parts (one persistent process, serialized submissions, the framing protocol) are already in place — and the first edition of this walkthrough is its own evidence. Three of the extensions it listed as futures have since shipped, each landing exactly where the design predicted:

  • Data files — shipped. The server resolves each session's cwd to the active document's directory at open time (falling back to $HOME only when no file is open), so plot 'data.dat' finds the file next to what you were editing. One assignment in openProcessView, no protocol change.
  • Export — shipped, as the renderer-only addition predicted: the right-click Save plot as… / Copy SVG menu, plus one pure module (svgWithIntrinsicSize) and one bridge method (gnuplotSaveSvg).
  • Print-friendly themes — shipped as the light and mono palettes: new behaviour landed in buildSubmission (a pure function with tests) plus one set-theme IPC, and the messy middle never changed.

Still genuinely open:

  • A session picker. Multiple sessions already work — every (gnuplot) call mints a fresh data-source and child — but today you navigate them by view name (C-x b), the tabline, or the minimap's thumbnails.
  • Replot on resize. The one missing capability. The SVG is rendered once at a fixed 720×480 and then CSS-scaled to the cell width. A true replot-on-resize would mean re-issuing the last submission for that cell at the new pixel width — but stateful sessions make "re-run the last line" subtly wrong, and a debounce would be needed to avoid a replot storm while dragging a divider. This is a design decision, not a typo-fix, and it should be flagged to the architect rather than guessed.

The through-line. Every extension above was (or will be) cheap precisely because of the pure/impure split this section opened with. New behaviour lands in buildSubmission (a pure function with tests) or in the renderer view (DOM, observable in the running app), and the messy middle — spawn, framing, temp files, reaping — does not have to change. That is what "tested where it can be, honest where it can't" buys you.
