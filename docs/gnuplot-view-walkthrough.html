    Motivation: an interactive gnuplot notebook inside jmacs

    gnuplot is one of those tools you reach for in bursts. You want to see sin(x), then sin(x), cos(x), then the same thing with a title and a tighter yrange — each command a small refinement of the last. The natural shape of that work is a conversation: a running session you talk to, where earlier commands stay on screen and the next one builds on them. A one-shot gnuplot script.gp invocation throws that context away every time. An interactive terminal session keeps the process alive, but on most platforms gnuplot's interactive plot lands in a separate OS window that floats outside the editor, has its own dark/light assumptions, and disappears the moment you plot again.

    What we build in this walkthrough is the middle path: a gnuplot view that lives inside jmacs as a notebook REPL. One long-lived gnuplot child process per view; an input line at the bottom; and a scrolling transcript above it where every command you submit becomes a cell holding its result — an inline SVG plot, text output from print/show, or a red error. The plot renders in the document, themed to match the editor, and it stays put. Your previous five plots scroll up; you can read your whole exploratory session at a glance.

    The Lisp command that opens one — the entire user-facing surface:

    (defcommand gnuplot ()
  "Open a fresh gnuplot buffer.

   The buffer that appears is shown through the L4 gnuplot view (not the
   text editor view) — a notebook REPL. Type a gnuplot command at the
   input line and press Enter to run it; the plot (or text / error
   output) appears as a cell above. Use Up and Down to recall previous
   commands; press C-c to interrupt a long-running plot.

   Each call to `gnuplot` creates a new buffer — switch back to an open
   one by name with `C-x b`. If gnuplot is not installed, the view shows
   install instructions (`brew install gnuplot`)."
  (open-gnuplot-buffer!))

    You invoke it with M-x gnuplot or the chord C-c g, bound by symbol in the c-c-keymap so the command resolves at dispatch time and load order never matters: 

    (define c-c-keymap
  {"tab"       'toggle-fold-at-point
   ;; ...
   ;; C-c g opens a gnuplot buffer (see gnuplot.lisp). Bound by symbol;
   ;; the command resolves at dispatch time, so load order doesn't matter.
   "g"         'gnuplot})

    Why a notebook, and why these specific design choices

    The view deliberately mirrors jmacs's existing shell view — same factory-plus-custom-element shape, same hide-not-kill lifecycle — but the interaction model is different, and that difference drives every decision in the rest of this walkthrough. A shell streams raw pty bytes into an xterm grid; there's no notion of "one command, one result." gnuplot in pipe mode does have that notion: you feed it a command, it draws a plot and maybe prints some text. So instead of a terminal grid, the view is built from three parts, called out in its own file header: 

    // instead of an xterm grid the view holds:
//   - a header (chart icon + buffer name),
//   - a scrollable transcript of per-command cells, and
//   - a bottom input line with its own command history (Up/Down).

    Three consequences fall out of choosing a notebook over a terminal, and each is a section of this walkthrough:

    • The host must frame each submission, not just forward bytes. A terminal can pipe stdout through verbatim; a notebook needs to know when one command's output ends and the next begins. The host wraps every user command in a preamble/epilogue that routes the plot to a temp SVG file and emits two sentinel tokens, and a submission only completes when both sentinels arrive. That's the protocol layer.
    • The view needs its own command history. The shell view keeps no history — the child shell's readline owns Up/Down. A bare <input> has no readline, so we implement a small history ring ourselves (and unit-test it without a DOM).
    • The plot must be themed by us, not by gnuplot's defaults. gnuplot's stock SVG is white-on-white. To sit in a dark editor it has to be re-themed at render time — a dark background baked into the SVG, axis and grid colours, and a redefined line-type palette so a bare plot sin(x), cos(x) picks up two distinct, legible colours.

    A tour of the finished view

    The three regions, top to bottom: a header with a chart icon and the buffer name, the scrolling transcript of result cells, and the persistent input line. The first cell is a plot; the second an error (red); the third text-only output.

    Each region is constructed directly in createGnuplotView. The transcript and input line are plain DOM the view appends to its root — nothing exotic: 

    // Transcript: a scrolling column of per-command cells.
const transcriptEl = doc.createElement('div');
transcriptEl.className = 'gnuplot-transcript';
root.append(transcriptEl);

// Input line: a prompt + a plain text input.
const inputRow = doc.createElement('div');
inputRow.className = 'gnuplot-input-row';
const prompt = doc.createElement('span');
prompt.className = 'gnuplot-prompt';
prompt.textContent = 'gnuplot>';
const input = doc.createElement('input');
input.type = 'text';
input.className = 'gnuplot-input';
inputRow.append(prompt, input);
root.append(inputRow);

    A cell is created the moment you press Enter — echoed with its command and marked pending — and keyed by the submission id the host will later echo back. When the result arrives, it's matched to that cell and filled in. This echo-then-fill pattern is what makes the session feel responsive even though the plot render is asynchronous: 

    function runCommand(cmd) {
  if (!buffer || buffer.ended) return;

  const cell = doc.createElement('div');
  cell.className = 'gnuplot-cell gnuplot-cell-pending';
  // ...echo the command into the cell...
  transcriptEl.append(cell);
  scrollToEnd();

  // We track our own parallel counter so we can key the cell before the
  // result returns.
  buffer.submitCounter = (buffer.submitCounter ?? 0) + 1;
  const id = buffer.submitCounter;
  cellsById.set(id, cell);

  if (writeFn) {
    writeFn(buffer.sessionId, cmd).catch(() => {
      markCellError(cell, '[gnuplot write failed]');
    });
  }
}

    A cell can end up as any one of four shapes — a plot, text, an error, or a dim (no output) acknowledgement for a bare set — and the same result handler decides which, based purely on what the host sent back in the { svg, text, error } payload. The plot SVG is inlined (not wrapped in an <img> data-URL) so it scales with the cell; it's trusted-local markup with <script> already stripped main-side: 

    // The SVG is trusted-local (generated by the host's own gnuplot,
// scripts already stripped main-side); inline it so it scales with the cell.
if (typeof payload.svg === 'string' && payload.svg !== '') {
  const plot = doc.createElement('div');
  plot.className = 'gnuplot-cell-plot';
  plot.innerHTML = payload.svg;
  cell.append(plot);
}

    The dynamic option on gnuplot's svg terminal makes that scaling actually work — the SVG declares a viewBox rather than fixed pixel dimensions, so the stylesheet can let it fill the cell width and grow its height to match: 

    .gnuplot-cell-plot svg {
  display: block;
  max-width: 100%;
  height: auto;
}

    When gnuplot isn't installed

    A view that hard-crashes when its backing tool is missing is a bad citizen in an editor people open every day. gnuplot is frequently not installed, and spawn('gnuplot', …) doesn't even throw synchronously for a missing binary — it emits an async error event with code === 'ENOENT' a tick later. The host turns that into a distinct exit signal, and the view replaces its transcript with a friendly install card and disables the input rather than showing a stack trace: 

    if (payload.notInstalled) {
  transcriptEl.replaceChildren();
  cellsById.clear();
  const card = doc.createElement('div');
  card.className = 'gnuplot-not-installed';
  // ...chart icon + message...
  msg.textContent = payload.message ?? DEFAULT_NOT_INSTALLED;
  card.append(icon, msg);
  transcriptEl.append(card);
  input.disabled = true;
  input.placeholder = 'gnuplot unavailable';
  return;
}

    This graceful-degradation path is the one piece of the feature that's live-verified on the build machine — gnuplot is not installed there, so opening the view with C-c g really does land on the install card. The plot-rendering paths are unit-tested as pure logic (26 cases covering quoting, submission framing, the SVG-has-plot heuristic, the stream demux, and the history ring) and await a live brew install gnuplot for end-to-end confirmation.

    What you'll learn in this walkthrough

    • How to host a long-lived subprocess from Electron's main process — one gnuplot child per view, keyed by a renderer-generated session id, with spawn / write / signal / kill exposed over the context bridge and results pushed back as async IPC.
    • The notebook submission protocol — why each command is wrapped with a preamble/epilogue, how the plot is routed to a temp SVG via set output / unset output, and why a submission completes only when both a stdout and a stderr sentinel arrive.
    • Stream demultiplexing as pure logic — a SubmissionDemux state machine that consumes stdout/stderr line by line, survives sentinels split across chunks, and is unit-testable with no subprocess and no DOM.
    • Theming a foreign tool's output to match the editor — the dark set linetype palette baked into every submission, the self-contained SVG background, and the svgHasPlot heuristic that distinguishes a real plot from an empty header-only file.
    • The custom-element view, its history ring, and chord forwarding — how <gnuplot-view> follows jmacs's hide-not-kill lifecycle, how the input line recalls history with Up/Down, and how non-printing chords (C-x b, M-x) still reach the host keymap while the input is focused.
    • Wiring a new view kind into the app shell — registering the singleton view, the per-kind configure factory, the open-gnuplot-buffer! bridge, and the kill-branch that reaps the gnuplot child so it doesn't leak.
    • Graceful degradation — turning an async ENOENT into a calm install card instead of a crash.

    With the motivation and the finished shape in view, the next section drops down to the host: spawning the gnuplot child and the IPC surface that the view talks to.

    Architecture: what a "view kind" actually is in jmacs

    Before any gnuplot code, you have to understand the shape of the hole you are filling. In jmacs, the editor does not have one canvas that everything draws into. It has a family of view kinds — text, image, pdf, browser, jukebox, directory-tree, shell — and a new kind is not a special case bolted onto the editor core. It is an assembly of four small, independently-replaceable parts that already have well-defined seams. The gnuplot view is the seventh-or-so kind to be built against those seams, and the discipline of the build was to add nothing new to the framework: every part of gnuplot slots into a socket that the shell view defined first.

    A view kind, concretely, is these four things:

    1. A renderer custom element (L4) — a <gnuplot-view> DOM element that owns the on-screen surface and the user interaction. It knows nothing about subprocesses or IPC channel names; it is handed a bag of callbacks.
    2. A host configure-factory — a plain function in app.js (configureGnuplotView()) that fills that bag of callbacks with the real IPC bindings, so the element can be tested with fakes and run with the real bridge.
    3. A main-process host — the privileged side (gnuplot.js) that owns the actual gnuplot child process, the filesystem, and the dangerous powers the renderer is not allowed to touch.
    4. A Lisp surface — the (gnuplot) command, a mode label, and a keybinding, which is how the kind becomes reachable to the user without hard-coding it into the host.

    The rest of this section walks each part in the order data flows through it, and at every step names the shell-view precedent that shaped the decision. Where the shapes diverge, the divergence is the interesting part — it tells you what is essential to a view kind versus what was incidental to terminals.

    The big picture

    The data path: a Lisp command mints a session and a view record; the custom element renders it; the configure-factory supplies IPC bindings; the context bridge is the only door to the main process; the host owns the child. Each box is replaceable without touching its neighbours.

    1. The renderer custom element — and why it owns no powers

    The view is an HTML custom element, <gnuplot-view>, that extends a shared ViewElement base. The element is deliberately ignorant: it never imports electron, never names an IPC channel, never spawns anything. It is handed a plain options object of callbacks at configure() time and it calls those. That is the whole contract. 

    export class GnuplotView extends ViewElement {
  configure(options) {
    if (this._inner !== null) {
      throw new Error('GnuplotView.configure: cannot reconfigure after mount');
    }
    this._options = options ?? null;
  }

  get kind() {
    return 'gnuplot';
  }

  connectedCallback() {
    if (this._inner !== null) return;
    this._inner = createGnuplotView(this, this._options ?? {});
    if (this._pendingBuffer !== null) this._inner.setBuffer(this._pendingBuffer);
  }

    packages/renderer/src/gnuplot-view.js — the custom-element wrapper

    Why split configure() (set the callbacks) from connectedCallback() (build the DOM)? Because a jmacs view is created once and mounted many times. The element is constructed and configured eagerly at startup; the actual inner DOM and history are not built until the element is first connected to the document. That is the first place the shell precedent shows through — <shell-view> has the identical configure-then-build split, for the same reason.

    The element is a thin shell around a closure-based factory, createGnuplotView(container, options), which builds the three real pieces of UI: a header, a scrolling transcript of cells, and a bottom input line. This factory boundary is what makes the view testable without Electron at all — you can hand createGnuplotView a jsdom container and fake spawn/write/onResult functions and drive the whole notebook in a unit test. (The command-history ring it uses is itself extracted into a pure createHistory() with its own nine-case suite — pure logic comes out of the DOM wherever it can.)

    The load-bearing rule: the renderer is sandboxed and untrusted. It cannot read files, cannot spawn processes, cannot run the SVG terminal. Everything dangerous lives behind the context bridge in the host. The view's only privilege is "ask the host to do something, and render what comes back." This is not gnuplot-specific; it is the Electron security model, and every view kind obeys it. It is the reason the architecture is split at all.

    2. The configure-factory — the IPC seam made explicit

    The element wants callbacks; the host exposes IPC. The configure-factory is the one place those two are married. It is a plain function in app.js that returns the options bag, wiring each renderer callback to the corresponding window.host.* bridge method, with a graceful fallback when the bridge is absent (so the view degrades instead of throwing in a browser harness): 

    function configureGnuplotView() {
  return {
    spawn: (sessionId, opts) =>
      window.host && typeof window.host.gnuplotSpawn === 'function'
        ? window.host.gnuplotSpawn(sessionId, opts)
        : Promise.resolve({ ok: false, error: 'gnuplot IPC unavailable' }),
    write: (sessionId, data) =>
      window.host && typeof window.host.gnuplotWrite === 'function'
        ? window.host.gnuplotWrite(sessionId, data)
        : Promise.resolve({ ok: false }),
    signal: (sessionId) => /* … gnuplotSignal … */,
    kill:   (sessionId) => /* … gnuplotKill … */,
    onResult: (callback) => /* … onGnuplotResult … */,
    onExit:   (callback) => /* … onGnuplotExit … */,
    ...(keymapReady ? { onKey: dispatchKey } : {}),
  };
}

    apps/desktop/src/app.js — the host configure-factory

    Put this next to configureShellView() and the shapes are almost identical — both return spawn / write / kill / onExit plus a stream callback. Two differences carry the whole design distinction between a terminal and a notebook:

    • The shell returns onData — a raw byte stream; the gnuplot view returns onResult — a structured, one-per-submission payload { id, svg, text, error }. That single rename is the difference between "stream a pty into an xterm grid" and "submit a command, get back one cell."
    • The shell carries resize (cols/rows for the pty); gnuplot has no pty, so there is no resize. Instead it carries signal (C-c → SIGINT to interrupt a running plot) and onKey, a chord-forwarding callback so the host keymap (C-x b to switch buffers, etc.) still fires while a plain <input> has focus — the same trick the browser view's URL bar uses.

    The factory is not called once. It is the reusable recipe: a singleton gnuplotView element is created and configured at startup, and the very same factory is handed to the tabline mount path so each per-tab <gnuplot-view> gets its own freshly-bound callbacks. That is why the wiring lives in a named function and not inline.

    3. The IPC split and the context bridge

    The renderer and the main process never share memory; they speak only over Electron IPC, and the renderer can only reach IPC through the context bridge set up in preload.mjs. The bridge exposes a small, named, audited surface — not ipcRenderer itself — so the renderer gets exactly these functions and nothing else (no require, no fs). The gnuplot surface is six methods, split into two directions: 

    // renderer → host (invoke/return):
gnuplotSpawn:  (sessionId, options = {}) =>
  ipcRenderer.invoke('gnuplot:spawn',  { sessionId, cwd: options.cwd }),
gnuplotWrite:  (sessionId, data) =>
  ipcRenderer.invoke('gnuplot:write',  { sessionId, data }),
gnuplotSignal: (sessionId) =>
  ipcRenderer.invoke('gnuplot:signal', { sessionId }),
gnuplotKill:   (sessionId) =>
  ipcRenderer.invoke('gnuplot:kill',   { sessionId }),

// host → renderer (subscribe, returns an unsubscribe fn):
onGnuplotResult: (callback) => {
  const handler = (_event, payload) => callback(payload);
  ipcRenderer.on('gnuplot:result', handler);
  return () => ipcRenderer.removeListener('gnuplot:result', handler);
},
onGnuplotExit:   (callback) => { /* same shape on 'gnuplot:exit' */ },

    apps/desktop/src/preload.mjs — the gnuplot bridge surface

    The asymmetry is deliberate and is the core of the IPC model:

    • Renderer → host calls are request/response (invoke ⇒ ipcMain.handle). "Spawn this," "submit this command," "kill this" — each is a one-shot with an acknowledgement. The renderer is asking permission.
    • Host → renderer calls are an event stream (webContents.send ⇒ ipcRenderer.on). Results and exits arrive whenever the host has them, possibly long after the write that triggered them returned. The on* subscriptions return an unsubscribe function — the view calls it on destroy(), which is how the IPC listeners do not leak across the view's many mount/unmount cycles.

    Each write is fire-and-forget at the IPC layer: it returns { ok } immediately, and the actual plot comes back asynchronously on gnuplot:result, matched to its cell by the submission id the host echoes. This is why the view keeps a cellsById Map — the result can arrive out of band, and the id is how it finds the cell its command created. The shell uses the identical invoke/send split (shell:spawn/write/kill inbound, shell:data/exit outbound); gnuplot did not invent a new IPC discipline, only new channel names and a richer payload.

    4. Lifecycle: spawn, mount, kill — and "hide, don't kill"

    A gnuplot view has three distinct lifecycles that are easy to conflate and must be kept separate. Getting this wrong is the bug family that docs/VIEWS.md exists to prevent.

    Spawn is lazy and tied to the first mount, not to creation. The Lisp command only creates a buffer record with a fresh session id and spawned: false; no process exists yet. The child is spawned the first time the view actually shows the buffer: 

    function setBuffer(next) {
  buffer = next;
  // …
  if (!buffer.spawned && !buffer.ended && spawnFn) {
    buffer.spawned = true;            // latch so we spawn exactly once
    spawnFn(buffer.sessionId, { cwd: buffer.cwd })
      .then((result) => { /* on !ok, mark ended + disable input */ })
      .catch(() => { /* host's onExit surfaces not-installed/error */ });
  }
}

    packages/renderer/src/gnuplot-view.js — spawn-on-first-mount

    The spawned flag lives on the buffer record, not the element, precisely because the element is re-mounted as the user moves the tab around. If the latch lived on the element it would re-fire and spawn a second process. The session id is minted host-agnostically in Lisp/app.js (nextGnuplotSessionId() → gnuplot-<n>-<timestamp>) and is the stable key the host uses to find the same child on every later write.

    Mount-moves hide, they do not kill. When a tab is dragged out of view, jmacs moves the element to an off-screen "warehouse," firing disconnectedCallback. For a gnuplot view that callback is intentionally empty: 

    /** Hide-not-kill — the gnuplot process stays alive; only the DOM-tree
 *  position changed. A later `connectedCallback` finds `_inner` set
 *  and is a no-op. */
disconnectedCallback() {
  /* intentionally empty */
}

    packages/renderer/src/gnuplot-view.js — hide-not-kill

    This is the single most important invariant the shell view established and the gnuplot view inherits: a view's process and transcript outlive its on-screen position. Tabbing away from a long-running plot, switching buffers, splitting panes — none of it touches the gnuplot child. The user comes back to exactly the transcript they left. If you reaped the process on disconnectedCallback you would get a one-line "fix" that silently kills the user's session every time they look at another tab. (connectedCallback guards on this._inner so a re-mount is a no-op, not a rebuild.)

    Only an explicit kill reaps the child. The process dies when the buffer is killed (C-x k), which routes through one central place, disposeKindView in app.js: 

    function disposeKindView(view, context) {
  if (!view || typeof view.kind !== 'string') return;
  if (view.kind === 'shell')   { /* … window.host.shellKill(view.sessionId) … */ }
  if (view.kind === 'gnuplot') {
    if (typeof view.sessionId !== 'string') return;
    try {
      if (window.host && typeof window.host.gnuplotKill === 'function') {
        window.host.gnuplotKill(view.sessionId);
      }
    } catch { /* Process is already gone — nothing to do. */ }
    return;
  }
  // …
}

    apps/desktop/src/app.js — kill routes through one place

    The renderer's own destroy() only drops the IPC subscriptions and clears cellsById; killing the process is a separate, host-side concern reached through gnuplotKill. Keeping "free renderer memory" and "reap the OS process" as two different actions is what lets hide-not-kill work at all: unmounting must be cheap and reversible, while killing is final and explicit.

    The shell-view as precedent

    Almost every decision above traces back to shell.js / shell-view.js. The gnuplot host even opens by naming the debt: it "mirrors shell.js's session bookkeeping (a sessions Map keyed by a renderer-generated id, webContents.send for output, ipcMain.handle for spawn/write/kill, a window-close reaping the orphans)." The correspondences are one-to-one:

    • session id minted in the renderer, host keys a Map off it;
    • invoke inbound, send outbound, with on* returning an unsubscribe;
    • spawn-on-first-mount latched on the buffer record;
    • hide-not-kill disconnectedCallback;
    • kill reaped through disposeKindView;
    • C-c → host signal; chord-forwarding so the host keymap survives a focused input;
    • a row in the one-place SINGLETON_VIEWS table ({ kind: 'gnuplot', el: gnuplotView, releasesBuffer: true }), right under the shell's, so display-toggling and buffer-release work with zero new dispatch code;
    • graceful degradation when the binary is missing — the shell has its "pipe fallback, no pty" note; gnuplot has its not-installed card.

    The single deep divergence is the interaction model, and it is the point of the whole walkthrough. The shell forwards raw pty bytes into an xterm grid — an unstructured stream. gnuplot is a notebook: each submission produces exactly one result, so the host cannot just forward chunks. It must frame each submission — wrap the user's command in a preamble that routes the plot to a temp SVG and an epilogue that emits stdout/stderr sentinels — and emit one structured gnuplot:result when both sentinels arrive. That framing protocol is what the next section dissects. Everything around it is shell, reused.

    The Lisp surface: how the kind becomes reachable

    A view kind that the host can build is useless until a user can summon it, and in jmacs that last mile is Lisp, not host code. The (gnuplot) command is a few lines and does nothing but call the host primitive that mints the buffer:

    packages/stdlib/lisp/gnuplot.lisp — the Lisp surface

    The split is the point: gnuplot.lisp is "just the Lisp surface for invoking" the view; the view itself is host/renderer code. The keybinding is equally hands-off — C-c g binds to the symbol 'gnuplot, not a function reference, so the command resolves at dispatch time and load order does not matter: 

    ;; C-c g opens a gnuplot buffer (see gnuplot.lisp). Bound by symbol;
;; the command resolves at dispatch time, so load order doesn't matter.

    packages/stdlib/lisp/keymap.lisp — C-c g

    A gnuplot-mode with the label "Gnuplot" exists only to give the modeline something to show — its own comment notes the buffer "is shown through the L4 gnuplot view … not the editor view, so no text-buffer keymap applies." That a whole view kind is reachable, and rebindable, entirely from the stdlib Lisp — without recompiling the host — is the editor's extension story working as designed, and it is why the Lisp surface counts as the fourth essential part of a view kind rather than an afterthought.

    Driving gnuplot: the long-lived pipe and the SVG protocol

    By this point in the walkthrough we have a gnuplot-kind buffer and a custom element to display it. What we do not yet have is the hard part: a reliable conversation with an external program that was never designed to be embedded. gnuplot in pipe mode is a line-oriented REPL. It reads commands from stdin, writes print output to stdout and diagnostics to stderr, and — crucially — gives you no framing. There is no "command N finished" marker, no exit code per command, no length prefix on its output. It just talks until it has nothing more to say, and "nothing more to say" looks exactly like "still thinking."

    The job of this layer is to impose a request/response discipline on a stream that has none, and to do it in a way that is testable without gnuplot even being installed. That last constraint shaped the whole design, so it is worth stating the split up front:

    • apps/desktop/src/gnuplot-protocol.js — pure, DOM-free, Electron-free logic: how to frame a submission, how to decide an SVG is real, and the stream demultiplexer that recognises when a submission is done. No subprocess, no IPC. This is what the 17 unit tests exercise.
    • apps/desktop/src/gnuplot.js — the host glue: one long-lived child per session, temp-file capture, IPC, and the not-installed degradation path. It uses the protocol module but contains none of its logic.

    This is the same instinct that runs through jmacs's other host views: keep the bytes-and-state-machine logic in a module a plain node --test can import (it can't resolve the @editor/* workspace packages or spin up Electron), and keep the Electron-shaped glue thin enough that there's little left to test live. gnuplot is not installed on the build machine, yet 26 cases of protocol behaviour are green.

    One process per session, strictly serialized

    Each gnuplot buffer owns exactly one gnuplot child, spawned lazily on first mount and kept alive for the life of the buffer. We do not spawn a fresh gnuplot per command. That matters for the design: gnuplot is stateful — sets, variables, and ranges accumulate across commands — and a notebook REPL is only useful if set xrange [0:10] still applies to the next plot. A long-lived process is what gives the view its REPL character. 

    const child = spawn('gnuplot', [], {
  cwd,
  env,
  stdio: ['pipe', 'pipe', 'pipe'],
  detached: false,
});

    Two details in the spawn are load-bearing. First, stdio is three plain pipes — no pseudo-terminal. gnuplot's pipe mode wants stdin/stdout/stderr, not a tty, so unlike the shell view there is no PTY, no resize channel, and no native addon to build. Second, the environment: 

    // GNUTERM=unknown stops gnuplot trying to auto-select an interactive
// terminal (qt/x11/wxt) at startup. We set the real `svg` terminal per
// submission anyway.
const env = { ...process.env, GNUTERM: 'unknown' };

    Without GNUTERM=unknown, a freshly started gnuplot may try to open an interactive window terminal (Qt, X11, wxWidgets) on startup, which is exactly wrong inside an Electron child. We pin the terminal to unknown at launch and then declare the real svg terminal on every submission, so startup never reaches for a GUI.

    Submissions are strictly serialized. A user command is not written to stdin directly; it is pushed onto a per-session queue and a pump only starts the next job when the demultiplexer is idle: 

    function pump(sessionId) {
  const entry = sessions.get(sessionId);
  if (!entry || entry.dead) return;
  if (entry.demux.busy || entry.queue.length === 0) return;
  // ... shift the job, build sentinels, set demux.begin({ onComplete }),
  //     write the framed program to gnuplot's stdin ...
}

    Serialization is what makes the framing tractable. Because gnuplot processes its stdin in order and we never have two submissions in flight, every byte that arrives on stdout/stderr unambiguously belongs to the one active submission. There is no need to interleave or correlate; the demux only ever tracks a single job.

    The submission frame: preamble, user text, sentinel epilogue

    Here is the heart of the protocol. Each user command is wrapped by buildSubmission into a small gnuplot program. The user's text goes in verbatim and unmodified in the middle; everything around it is framing we control. 

    export function buildSubmission(params) {
  const { userText, tmpFile, sentinelOut, sentinelErr,
          width = 720, height = 480 } = params;
  const term =
    `set terminal svg size ${width},${height} dynamic enhanced ` +
    `background rgb '${SVG_BACKGROUND}' font 'sans,11'`;
  return [
    term,
    `set output ${quoteGnuplot(tmpFile)}`,
    DARK_THEME_BLOCK,
    userText,                         // verbatim, unmodified
    'unset output',                   // flush + close the SVG (mandatory)
    "set print '-'",
    `print ${quoteGnuplot(sentinelOut)}`,        // "submission complete" -> stdout
    "set print '/dev/stderr'",
    `print ${quoteGnuplot(sentinelErr)}`,        // "stderr flushed"       -> stderr
    "set print '-'",
    '',                               // trailing newline
  ].join('\n');
}

    Reading the sequence top to bottom, each line earns its place:

    • set terminal svg ... — re-declares the SVG generator on every submission. We don't trust the terminal to persist across commands; declaring it each time makes a submission self-contained. dynamic makes the SVG scale to its container rather than baking a fixed pixel size; enhanced enables superscripts/markup in labels; the baked background rgb '#1e2228' is what makes the image dark on its own (more below).
    • set output <tmpFile> — redirects the plot bytes to a temp file rather than to stdout. This is the single most important design choice in the protocol. SVG is XML; if it came back interleaved on stdout with print text, we'd have to parse a mixed stream. Routing the binary-ish plot to a file leaves stdout/stderr carrying only textual output and our sentinels.
    • the dark-theme block — injected after set output and before the user text, so the palette is in effect when the user's plot runs but the user can still override it.
    • unset output — mandatory, and a classic gnuplot footgun. gnuplot buffers the SVG; the file is not complete (no closing </svg>) until the output is closed. Forgetting this line yields a truncated file every time.
    • the sentinel epilogue — the framing proper, covered next.

    Sentinel framing: completion gated on BOTH streams

    Since gnuplot won't tell us when a command is done, we make it tell us — by appending two print statements whose output we recognise. The tokens are deliberately long and unguessable so they can't collide with real user output: 

    export function sentinelsFor(id, nonce) {
  return {
    stdout: `__JMACS_GP_DONE__${id}__${nonce}__`,
    stderr: `__JMACS_GP_ERR__${id}__${nonce}__`,
  };
}

    A private prefix, the submission id, and a fresh 6-byte random nonce per submission. Even a user who deliberately prints our prefix can't forge the nonce.

    The subtle part is why there are two sentinels, one per stream. gnuplot writes errors to stderr, which is a separate pipe from stdout, and the two are not synchronised — when the stdout sentinel arrives, there may still be error bytes in flight on stderr. If we completed the submission the instant we saw the stdout sentinel, a real error could arrive a millisecond later and be misattributed to the next command's cell. So the epilogue prints a sentinel down each stream: 

    set print '-'            ; route print to stdout (fd 1)
print 'OUT_TOKEN'        ; "submission complete" lands on stdout
set print '/dev/stderr'  ; route print to stderr (fd 2)
print 'ERR_TOKEN'        ; "all stderr for this submission has been flushed"
set print '-'            ; restore stdout for the next submission

    gnuplot sends print output wherever set print last pointed: '-' is stdout, and the /dev/stderr device is fd 2. (One trap, verified against gnuplot 6: set print '-2' does not mean "fd 2" — gnuplot opens a file literally named "-2", so the stderr sentinel vanishes into that file and the submission hangs forever. The code uses /dev/stderr.) Because the error sentinel is printed after any diagnostics gnuplot emitted for the command, seeing it guarantees the stderr stream has been fully drained for this submission. A submission is therefore considered complete only when both sentinels have been observed — which is exactly what the demultiplexer enforces.

    The demultiplexer: a pure reducer over byte chunks

    Pipes deliver bytes in arbitrary chunks. A sentinel can be split across two data events; a single chunk can contain several lines. The SubmissionDemux absorbs all of that. It is a small line-buffered state machine with no DOM and no subprocess handle — which is exactly why it can be unit-tested against synthetic chunk sequences. 

    pushStdout(chunk) {
  this._outBuf += chunk;
  let nl;
  while ((nl = this._outBuf.indexOf('\n')) !== -1) {
    const line = this._outBuf.slice(0, nl);
    this._outBuf = this._outBuf.slice(nl + 1);
    const a = this._active;
    if (a && line === a.sentinelOut) {
      a.gotOut = true;
      this._maybeFinish();
    } else if (a) {
      a.stdoutLines.push(line);          // real user output
    }
  }
}

    It only acts on complete lines (terminated by \n); a trailing partial line stays in _outBuf until the rest arrives. That is what makes a split sentinel safe: 'OU' in one chunk and 'T\n' in the next reassemble into one line before the comparison happens. pushStderr is the mirror image. Completion is gated on both flags: 

    _maybeFinish() {
  const a = this._active;
  if (!a || !a.gotOut || !a.gotErr) return;   // need BOTH sentinels
  this._active = null;
  a.onComplete({
    stdout: a.stdoutLines.join('\n'),
    stderr: a.stderrLines.join('\n'),
  });
}

    The tests pin this behaviour precisely — that the stdout sentinel alone does not complete the submission ("must wait for BOTH sentinels"), that a sentinel split across chunk boundaries still reassembles, that two submissions run back-to-back through the same demux, and that stray output arriving with no active submission is simply ignored rather than buffered into the next job.
