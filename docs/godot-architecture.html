Architecture, for the VS Code generation

What Godot is, and why it isn’t shaped like your editor

A programmable text editor in the lineage of Emacs — rebuilt clean on web technology — written for people who think of their editor as something to shape, not just configure. If you’ve never touched Emacs, good: this explains it in terms of tools you already know.

The one-paragraph version. In VS Code or Sublime, the editor is a finished application and your extensions run outside it, talking through a fixed API. In Godot, the editor is the runtime of its own extension language. Every keystroke runs a command; every command is a piece of Lisp you can read; and you can redefine any of it — the keymap, a motion command, how a file is opened — while the editor is running, with no reload and no privileged core that’s off-limits. Everything below is a consequence of taking that one idea seriously.

01The mental-model shift

The fastest way to understand Godot is to notice where it puts the boundary between “the editor” and “your code.”

VS Code is a beautifully engineered app with a sandbox bolted to the side. Your extension is a separate Node process. It receives a curated vscode.* API, can’t touch what the API doesn’t expose, and to apply a change you reload the window. settings.json is a sealed negotiation: you pick from options the authors anticipated. Sublime is faster and lighter, with Python plugins, but the same shape — a native core you extend from the outside.

Godot inverts this. There is no privileged core and no process boundary between you and the editor. The commands you invoke, the standard library, the keymap — all of it is ordinary Lisp loaded into the same runtime your own code runs in. Open the editor’s built-in REPL, evaluate a new definition, and the next keystroke uses it. The thing you are editing in is the program, and it is open all the way down.

A few Emacs-rooted words appear throughout. Here they are in your vocabulary:

bufferAn in-memory document model. Like VS Code’s TextDocument, but richer — it carries cursors, selections, semantic metadata, modes, and edit history as first-class state, not as editor-side decorations.
viewAn on-screen surface showing a buffer (or other source). Usually a text editor — but also an image, a shell, an emulator, a notebook. The peer of an editor tab.
minibufferThe one-line input strip at the bottom for prompts and commands — essentially the command-palette input, plus every “type a path / a name / a search” prompt.
M-x“Run a command by name.” The command palette. (M- = the Meta key; on this Mac build, Command.)
modeA bundle of behavior for a buffer. A major mode ≈ a language mode (Markdown, LaTeX); minor modes are toggleable layers (a linter, a preview) that stack on top.
point / markThe cursor position, and the other end of a selection. “Region” = the selection between them.
kill / yankCut/copy and paste — but onto a ring of recent cuts you can cycle through, not a single clipboard slot.

02The architecture in layers

Godot has a deliberately small shape you can hold in your head — five layers, each with one job and a stable seam to the next.

L0Host — Electron. File I/O, subprocesses, OS integration. Thin and stable.
L1Storage — the raw text data structure (a piece tree). Fast edits, undo, no idea what the text means.
L2Buffer — the semantic model: markers, overlays, text properties, point/mark, modes, hooks. The system’s nervous system.
L3Lisp — an interpreter written from scratch in JS. The customization and command language. Hot-reloadable.
L4Renderer — projects buffer state into the DOM, turns input into commands. Tree-sitter syntax, virtualized lines.

Dataflow is one-directional and easy to trace: input becomes a command → the command edits the buffer (L2) → the buffer emits change events → the renderer updates. The renderer never mutates state directly; it only ever subscribes and paints. That single rule is why the display can be replaced wholesale without touching anything that defines behavior.

If you’re wondering about performance: the editor surface is plain DOM (no React per character), only visible lines exist in the DOM at all, each line is split into runs of same-styled text rather than per-character spans, and renders are batched to one per animation frame. Syntax highlighting is a real tree-sitter parse, the same engine VS Code-adjacent tools use, with results stored back on the buffer as metadata.

03Buffers, not documents

VS Code’s TextDocument is text plus a language id; everything else — decorations, folding, diagnostics — is the editor’s, layered on top and owned by the UI. Godot moves that intelligence into the buffer, where extensions can reach it.

  • Markers — positions that ride edits correctly. Drop a marker, type 500 lines above it, the marker still points at the same logical spot. Bookmarks, multi-cursor, and tracked references are all just markers.
  • Overlays & text properties — metadata attached to ranges. Text properties travel with the characters under copy/paste; overlays float independently. Syntax faces, fold markers, search highlights, semantic categories all live here.
  • Modes & hooks — a buffer carries its behavior. Hooks are named places (“before change”, “mode activated”) where extensions attach — the substrate for nearly every feature.
  • Command-level undo — transactions grouped by the command that caused them, over the storage layer’s finer-grained undo.

Because this is the layer both Lisp and JavaScript talk to, a feature you’d write as a heavyweight VS Code extension — tracking positions, decorating ranges, reacting to edits — is here a handful of calls against a model that was built to be programmed.

04Everything is a view (yes, even an emulator)

In VS Code, anything that isn’t a text editor is a webview — a sandboxed iframe with its own world, bolted onto the side and second-class. Godot has one general notion of a view, and a text editor is just the most common kind.

A view is the unit of “a thing you’re looking at”: it owns a surface, a lifecycle, and a place in the window. Most wrap a text buffer. But the same machinery hosts any web component as a first-class view — with roughly six lines of Lisp via define-element-view. Things that already exist as real, navigable views in Godot:

a live shell (xterm + PTY) an Atari emulator a reactive notebook an SVG drawing editor a PDF viewer a jukebox a bibliography search panel a code minimap

None of these is a special case in the core. Each is a view kind plugged into the same lifecycle as the text editor — it appears in the buffer list, splits into panes, restores across restarts, and is driven by the same command system. The window itself is a pane tree (a binary tree of splits, leaves holding views), so you compose layouts freely rather than fighting a fixed sidebar/panel grid.

The payoff isn’t “Godot ships an emulator.” It’s that the distance between “I have a web component” and “it’s a real, paneable, session-restoring view in my editor” is an afternoon — because views were designed as an open set, not a closed list the authors curate.

05One brain, many windows

Open two windows in VS Code and you have two independent processes that happen to share files on disk. Godot is built like a language runtime with a daemon.

The server (“the spine”)One process. Holds every buffer, the Lisp runtime, and all dispatch. The single source of truth.

A central server owns the buffers and the interpreter; each window is a thin client that paints what it’s told and forwards keystrokes. Two consequences fall out, both hard or impossible in the conventional model:

  • Shared, live state. The same buffer open in two windows is the same object. Type in one, the other updates as you type — not on save, not on a file-watcher tick. There is no “reconcile two copies” problem because there is only one copy.
  • The server resolves every key. A keystroke is sent to the server, which decides what it means and what should happen — then tells whichever windows it chooses. So a command in window A can act on B and C: close every other window, or retheme all of them, in one keystroke. The window is a display, not a brain.

This is the Emacs-daemon idea (one long-lived process, many lightweight frames) — but here it’s the foundation, with a clean message protocol between the server and its clients rather than a retrofit.

06Two languages, one runtime: Lisp for taste, JS for muscle

Godot is scriptable in two languages that share the same editor state — and the split between them is a deliberate design stance, not an accident of having both.

The custom Lisp is the primary surface: it’s what the standard library and every built-in command are written in, and it’s what gives the editor its character. The dialect is its own thing — Scheme’s lexical scoping and modules, Clojure’s data-structure idioms, lexically-scoped macros, immutable values by default, docstrings on every definition. JavaScript is equally first-class (you’re in a JS runtime; pretending otherwise would be silly) and is where heavy lifting and web-library integration naturally go.

The governing principle: Lisp is the customization and macro surface; JavaScript does the engine work; and the JS defaults must always be overridable from Lisp, live. A command registered in one language is callable from the other; both bind the same buffer API. You reach for JS when the task is web-shaped or performance-shaped, and Lisp when you’re shaping how the editor behaves.

A binding is data:

;; keymap.lisp — the keymap is a literal map of key → command name
{"M-f" 'forward-word
 "C-x C-f" 'find-file
 "C-h k" 'describe-key}

A command is an ordinary definition with a docstring:

(defcommand comment-line ()
  "Toggle line comments on the region or current line."
  ...)

And hosting a whole new kind of view is about this small:

(define-element-view atari     ; the symbol is the kind AND the command → M-x atari
  :title  "Atari 2600"
  :module ".../stella-element.js"   ; the ES module that defines the element
  :tag    "stella-emulator")       ; the custom element it registers

Redefine any of these in the running editor and the change takes effect immediately — the “hot reload” isn’t a dev-mode convenience, it’s how the editor is meant to be lived in.

07A keystroke’s journey

Concretely, here is what happens when you press a key — the whole loop, because it’s short enough to follow.

  1. The window turns the raw event into a normalized name — Cmd+→ becomes the string "M-right". That’s all the window decides; it does no interpretation.
  2. It sends that string to the server as a “key” message.
  3. The server’s dispatcher (Lisp) resolves it through the active keymaps — minor modes, then the major mode, then the global map — and finds it bound to forward-word.
  4. It runs that command, which moves point and edits buffer state.
  5. The buffer change fans out to every window showing that buffer, each repainting the affected lines on its next frame.

If a command’s effect is purely visual — open a panel, close a window — the server doesn’t edit a buffer; it sends an explicit directive to a chosen set of windows. Same pipeline, different terminus. Notice there’s no place in that loop where the window “knows” what a key means. That knowledge lives in one editable Lisp keymap, which is exactly why you can change it from inside.

08What this actually buys you

Differences in architecture only matter if they cash out in daily use. These do.

  • The fix-it loop collapses. Notice an annoyance, open the REPL, redefine the command, keep working. No rebuild, no extension-host restart, no “reload window.” Minutes, sometimes seconds — not a context switch.
  • The editor explains itself. Press C-h k then any key and Godot tells you which command runs and shows its documentation — read from the live definition, not a manual that drifted. Ask it what a command does and it answers from itself. (We built exactly this self-describing help into the bottom panel.)
  • Non-text tools are real citizens. A shell, a notebook, an emulator, an SVG editor live in panes beside your code, restore with your session, and obey the same commands — not iframes in a side dock.
  • Windows cooperate. Two windows on one buffer edit in lockstep; one keystroke can drive all of them. The daemon model, by default.
  • Nothing is off-limits. There is no “you can’t do that from an extension.” If the editor can do it, your code can too, because your code and the editor are the same kind of thing.

09The principle underneath it all

One idea resolves nearly every design dispute in Godot: legibility. The editor should be comprehensible to the people who use it — not merely open-source, but shaped so the architecture fits in your head, the language has rules you can state, the layers have clear jobs, and the system explains itself when you ask. When power and clarity conflict, clarity wins until profiling says otherwise.

The second commitment is aesthetic: beautiful by default. Not configurable-into-beauty — good fonts, colors, and spacing chosen by someone with taste, present the first second you open it. Both commitments serve the same end: an editor is an environment in which thought happens, and a tool you can think clearly in has to be clear itself, and pleasant enough to spend hours inside.

Godot is, unapologetically, a successor in spirit to Emacs — it takes Emacs’s deepest idea (the editor as a living thing you reshape from within) and rebuilds it on a clean foundation, shedding forty years of incidental complexity while there’s still time to make the choices deliberately.

10Honest about what it is

Scope & status

Godot is a solo, v0.1 project, built by one person for themselves and the handful of others who’ll recognize the idea. It is not trying to be VS Code, not chasing a mass audience, and not a commercial play. macOS is the supported platform today; Linux and Windows come later.

It is not Emacs-compatible: the Lisp is its own dialect, and Elisp packages don’t run here — deliberately, to avoid carrying decades of baggage. And there’s a real cost of entry: you’re learning a custom Lisp and a model where shaping your tools is the normal way to use them. That cost is the point — this is an editor for people who’d find that fun, the kind who’d have built it themselves given time.

If that’s you — you keep a directory of half-finished extensions, you find the line between “user” and “developer” of your editor artificial — Godot is built for exactly the way you already want to work.

Godot — a Lisp-extensible editor. Vanilla JavaScript (ES modules, no TypeScript), Electron, tree-sitter; local-first; an interpreter written from scratch. Architecture docs live in the repository under docs/ (start at docs/MAP.md).
